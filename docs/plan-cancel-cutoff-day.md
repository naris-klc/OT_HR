# แผน — วันตัดการยกเลิกและถอนใบ ตั้งได้ในหน้านโยบาย

**สถานะ: ออกแบบเสร็จ ยังไม่เขียนโค้ด** · ตัดสินร่วมกับผู้ใช้ 2026-09-14

โจทย์ตั้งต้นคือ *"การกด ยกเลิก/ถอนใบ ห้ามไม่ให้เกินวันที่ 3 ของทุกเดือน และตั้งค่าใน
หน้านโยบายได้ด้วย"*

สิ่งแรกที่การสำรวจตอบกลับมา และเปลี่ยนรูปโจทย์ทั้งอัน คือ **ในระบบนี้ ยกเลิก กับ
ถอนใบ ไม่ใช่ของสิ่งเดียวกัน** มันคือสองกลไกที่แบ่งกันด้วยเส้น *ลายเซ็นแรก* —
ก่อนลายเซ็นคือ `ยกเลิก` (ทำได้ทันที ใบตายเดี๋ยวนั้น) หลังลายเซ็นคือ `ขอถอนใบ`
(ยังไม่มีอะไรขยับ เป็นคำขอที่รอคนตอบ) และตัวหลังยังแยกเป็นสองจังหวะอีก คือ *ขอ*
กับ *ตัดสิน* รวมเป็นสามการกดที่ต้องตอบทีละอัน ไม่ใช่กฎเดียวแปะทับทั้งหมด

| HR ถอนแถวที่ระบบสร้าง (`void`) ติดด้วยไหม | **ไม่ติด** — ไม่ได้ถูกเลือก |
| วันที่ 3 นับเทียบกับเดือนไหน | **วันที่ 3 ของเดือนถัดจากงวดของใบ** |

| วันที่ 3 เอง ยังกดได้ไหม | **ยังกดได้ทั้งวัน** — ปิดตอนเที่ยงคืนขึ้นวันที่ 4 |

## 2. ข้อตึงที่ต้องพูดก่อน — ปิดงวด เคยถูกถอนออกไปแล้ว

**นี่คือกำแพงระดับเดือนตัวแรกที่กลับเข้าระบบ หลัง ปิดงวด ถูกถอนเมื่อ 2026-08-31**
ไม่พูดถึงข้อนี้ไม่ได้ เพราะหัวไฟล์ `lib/periodStatus.js` เขียนเหตุผลที่ HR ถอนมันไว้
ตรง ๆ ว่า **แฟ้มกระดาษ F-HR-027 ที่เซ็นแล้วคือตัวบันทึกจริง** ล็อกในฐานข้อมูล
ซ้อนอีกชั้นไม่ได้อะไร และมันไปขวางสิ่งที่ HR ทำบ่อยที่สุด คือกลับเข้าไปแก้แถวที่
บัญชีทัก

**ข้อนี้ไม่ใช่การเอา ปิดงวด กลับมา และความต่างวัดได้เป็นตัวเลข:**

- ปิดงวด ปฏิเสธ **เก้าทางเขียน** · ข้อนี้ปฏิเสธ **สามทาง** และทั้งสามเป็นทางของ
  *พนักงาน* กับ *ผู้เซ็น* ไม่ใช่ทางแก้ไขของ HR
- ปิดงวด ปิดหน้า HR ด้วย ต้องให้ผู้ดูแลระบบเปิดคืนพร้อมเหตุผล · ข้อนี้ **HR กับ
  admin ข้ามได้เสมอ ไม่ต้องขออะไรใคร** — สิ่งที่ HR บอกว่าต้องการ ยังอยู่ครบ
- ปิดงวด เป็น *สถานะของเดือน* ที่ต้องมีคนไปกด · ข้อนี้เป็น *เลขคณิตจากวันที่*
  ไม่มีอะไรให้กด ไม่มีโมเดลใหม่ ไม่มี collection ใหม่
- ปิดงวด ปิดทุกเดือนเท่ากัน · ข้อนี้ ship มาเป็น **ไม่กำหนด** พฤติกรรมวันที่ deploy
  เหมือนเดิมทุกประการ จนกว่า HR จะเลือกเปิดเอง

และหัวไฟล์เดียวกันนั้นบอกที่ทางของกฎแบบนี้ไว้ด้วย:

> *"if a future rule needs to STOP a write, it does not belong here — it belongs
> beside `editPermission`, with the other rules that say no."*

แผนนี้ทำตามนั้นตรงตัว — ดู §6

## 4. กฎ — เขียนเป็นเลขคณิตให้ไม่มีที่ให้ตีความ

### 4.1 นิยาม

ให้ `cancelCutoffDay` = D (เลข 1–15 หรือ `null`) และ `cancelCutoffGraceDays` = G

**วันสุดท้ายที่ใบยังยกเลิก/ถอนได้** คือวันที่มากกว่าระหว่างสองอัน:

```
วันตัดของงวด    = วันที่ D ของเดือนถัดจาก periodOf(entry.workDate)
วันตัดของการยื่น = วันที่ยื่นใบ + G วัน
วันสุดท้าย       = max(วันตัดของงวด, วันตัดของการยื่น)
```

- D เป็น `null` → **ไม่มีวันสุดท้าย** กฎทั้งข้อไม่ทำงาน (ค่าที่ ship)
- เปรียบเทียบแบบ `วันที่วัด <= วันสุดท้าย` — **วันที่ D เองยังกดได้ทั้งวัน**
  ปิดตอนเที่ยงคืนขึ้นวันถัดไป
- ทุกวันเป็นสตริง `'YYYY-MM-DD'` เวลาสำนักงาน ผลิตจาก `today()` เท่านั้น

### 4.2 วันที่วัด — ไม่ใช่ `today()` เสมอไป

นี่คือจุดที่คำตอบ *"ยื่นทันถือว่าทัน"* ลงมาอยู่ในโค้ด

| การกด | วัดที่วันไหน |
|---|---|
| ยกเลิกใบของตัวเอง | `today()` |
| ขอถอนใบ | `today()` |
| ตัดสินคำขอถอน (อนุมัติ **และ** ไม่อนุมัติ) | **`entry.withdrawal.requestedAt`** แปลงเป็นวันสำนักงาน |

ผลคือทางเดินปกติจะไม่มีวันโดนปฏิเสธที่ขั้นตัดสินเลย เพราะคำขอที่ยื่นไม่ทันถูก
ปฏิเสธไปตั้งแต่ขั้น *ขอ* แล้ว กฎที่ขั้นตัดสินจึงเป็นกำแพงชั้นสองที่มีไว้กันสองกรณี
ที่เอื้อมถึงได้จริง:

1. **คำขอที่ค้างอยู่ในฐานข้อมูลก่อนฟีเจอร์นี้ขึ้น** — ไม่เคยผ่านด่านขั้น *ขอ*
2. **HR แก้ `workDate` ข้ามเดือนหลังมีคำขอแล้ว** — `period` ขยับ วันตัดขยับตาม
   ใช้ `requestedAt` เป็นตัววัดทำให้คำขอที่เคยทันไม่กลายเป็นไม่ทันย้อนหลัง

### 4.3 ตัวอย่างเดินจริง (D = 3, G = 3)

| ใบ | `workDate` | งวด | วันที่ยื่น | วันตัดของงวด | วันตัดของการยื่น | **วันสุดท้าย** |
|---|---|---|---|---|---|---|
| ก | 2026-08-20 | 2026-08 | 2026-08-21 | 2026-09-03 | 2026-08-24 | **2026-09-03** |
| ข | 2026-09-12 | 2026-09 | 2026-09-13 | 2026-10-03 | 2026-09-16 | **2026-10-03** |
| ค | 2026-07-20 | 2026-07 | 2026-09-14 | 2026-08-03 *(ผ่านไปแล้ว)* | 2026-09-17 | **2026-09-17** |
| ง | 2026-12-28 | 2026-12 | 2026-12-29 | 2027-01-03 | 2027-01-01 | **2027-01-03** |

- ใบ **ก** วันที่ 2026-09-03 กดได้ · 2026-09-04 ปฏิเสธ
- ใบ **ค** คือเหตุผลที่ขั้นต่ำมีอยู่ ถ้าไม่มี ใบนี้จะยกเลิกไม่ได้เลยตั้งแต่วินาที
  ที่ถูกสร้าง ซึ่งคือกับดักที่ `maxPastSubmissionDays: null` เปิดทางไว้ให้
- ใบ **ง** พิสูจน์ว่าเลขคณิตข้ามปีต้องถูก D สูงสุด 15 จึงไม่ต้องคิดเรื่องเดือนสั้น

### 4.4 ค่าที่อ่านไม่ออก = ปิด

D ที่ไม่ใช่จำนวนเต็ม 1–28 ให้ถือว่า **ไม่กำหนด** ไม่ใช่ให้ถือว่าเข้มที่สุด

ตรงข้ามกับ `maxAdvanceSubmissionDays` ที่ค่าเสียแล้วตกไปที่คำตอบเข้ม และตรงกับ
`maxPastSubmissionDays` ที่ตกไปที่ผ่อน — ด้วยเหตุผลเดียวกับที่ `src/config/policy.js`
ให้ไว้: กฎที่พังแล้วล็อกคนออกจากใบของตัวเองแย่กว่ากฎที่พังแล้วไม่ทำงาน

## 5. นโยบายสองข้อใหม่

### 5.1 คีย์

```js
// src/config/policy.js — เพิ่มใน DEFAULT_POLICY
cancelCutoffDay: null,       // 1–28 หรือ null (ไม่กำหนด) — วันที่ของเดือนถัดจากงวด
cancelCutoffGraceDays: 3,    // ขั้นต่ำนับจากวันที่ยื่น
```

`cancelCutoffGraceDays` ship มาเป็น 3 ทั้งที่กฎปิดอยู่ เพราะมันไม่มีความหมายเดี่ยว ๆ
— วินาทีที่ HR เปิด `cancelCutoffDay` ขั้นต่ำต้องทำงานอยู่แล้ว ไม่ใช่ต้องไปเปิดอีกที

### 5.2 จัดประเภท — COSMETIC ทั้งคู่

ต้องเพิ่มใน `COSMETIC_KEYS` (`lib/policyVersion.js:70`) ไม่ใช่ `ARITHMETIC_KEYS`
มี `test/policyVersion.test.js:277` บังคับอยู่แล้วว่าทุกคีย์ต้องอยู่ลิสต์ใดลิสต์หนึ่ง
และห้ามอยู่ทั้งสอง — คอมมิตที่ลืมข้อนี้จะถูกเทสต์จับเอง

เหตุผลยกมาจากฝาแฝดที่ใกล้ที่สุดสองตัวคือ `maxAdvanceSubmissionDays` และ
`maxPastSubmissionDays` และมันแรงกว่าด้วยซ้ำ: กฎนี้ไม่ถูกส่งเข้า `computeSession`
เลย ไม่มี `segments` `buckets` หรือ `totals` ค่าไหนต่างไปแม้แต่นาทีเดียวไม่ว่าตั้ง
เป็นอะไร มันตัดสินแค่ว่า *ปุ่มกดได้ไหม*

และเหมือนฝาแฝดทั้งคู่ **การ replay ข้อนี้ทำไม่ได้แม้จะอยากทำ** — กฎถามว่าวันนี้
เป็นวันอะไร และ replay รันในวันที่ขยับไปแล้วเสมอ `savePolicy` replay เฉพาะคีย์เชิง
เลขคณิต การลงทะเบียนไว้ที่นี่จึงเป็นสิ่งที่กันไม่ให้มันถูกถาม

### 5.3 `cancelCutoffGraceDays` ต้องมีกฎ inert

ขณะ `cancelCutoffDay` เป็น `null` ขั้นต่ำไม่ถูกอ่านเลย — ซึ่งคือนิยามของ
`lib/policyInert.js` เป๊ะ ๆ: ดรอปดาวน์ที่ตั้งแล้วไม่มีอะไรเกิดขึ้น หน้าตาเหมือน
ดรอปดาวน์ที่ทำงาน เพิ่มกฎหนึ่งข้อใน `RULES`:

```js
cancelCutoffGraceDays(policy) {
  if (policy.cancelCutoffDay !== null && policy.cancelCutoffDay !== undefined) return null;
  return {
    text: 'ไม่ถูกอ่านกับค่าที่ตั้งอยู่ตอนนี้ — วันตัดการยกเลิกและถอนใบ ตั้งไว้ที่ '
      + '“ไม่กำหนด” จึงไม่มีวันตัดให้ผ่อนผัน · ค่าที่เลือกไว้ยังถูกเก็บ '
      + 'และมีผลทันทีที่ตั้งวันตัด',
    causes: ['cancelCutoffDay'],
  };
},
```

`test/policyInert.test.js:317` บังคับว่าคีย์ที่มีกฎ inert ต้องมีแถวใน `POLICY_FIELDS`
จริง และ `:306` ตรึงชุดแถวที่ inert ใต้ค่าตั้งต้นไว้ — ชุดนั้นจะกว้างขึ้นหนึ่งแถว
ต้องแก้ให้ตรง

### 5.4 บล็อกใหม่ §6 บนหน้านโยบาย

`POLICY_SECTIONS` (`components/AdminView.jsx:6085`) มีห้าบล็อก และบล็อก §5 ชื่อ
**กรอบเวลาการยื่นใบ OT**

## 6. ที่ทางของกฎในโค้ด

ทั้งหมดอยู่ใน `lib/entries.js` ข้าง `cancelPermission` ตามที่หัวไฟล์

และให้คอมโพเนนต์ import ได้ (เทสต์คอมโพเนนต์ในโปรเจกต์นี้อ่าน *ข้อความในไฟล์*
ไม่มี JSX transform กฎจึงห้ามอยู่ในคอมโพเนนต์)

```js
/** วันสุดท้ายที่ใบนี้ยังยกเลิก/ถอนได้ — 'YYYY-MM-DD' หรือ null เมื่อไม่กำหนด */
export function cancelDeadline(entry, policy = {}) { … }
```

### 6.1 เสียบเข้ากฎที่มีอยู่ โดยไม่ทำของเก่าพัง

ทั้ง `cancelPermission` และ `withdrawEligibility` **รับพารามิเตอร์ตัวที่สามเพิ่ม
แบบมีค่าตั้งต้น** ไม่เปลี่ยนลายเซ็นเดิม:

```js
cancelPermission(user, entry, { policy, on } = {})
withdrawEligibility(user, entry, { policy, on } = {})
```

ไม่ส่ง `policy` มา = ไม่มีวันตัด = พฤติกรรมเดิมทุกประการ **เทสต์เดิม 12 + 26 เคส
จึงผ่านต่อโดยไม่ต้องแตะ** ซึ่งเป็นสิ่งที่ต้องการ เพราะเคสพวกนั้นตรึงกฎที่ไม่ได้
กำลังเปลี่ยน

### 6.2 ลำดับการตรวจ — HR ต้องถูกปล่อยก่อน

ใน `cancelPermission` สาขา `mayCorrectEntries(user) && isUntouchedSystemFiling(entry)`
อยู่บนสุดอยู่แล้ว และต้องอยู่ต่อไป การตรวจวันตัดต้องไปอยู่ **หลัง** การตรวจความเป็น
เจ้าของ และมีบรรทัดปล่อย HR/admin ของตัวเองก่อนเสมอ:

```js
if (mayCorrectEntries(user)) return null;   // ข้างใน cancelCutoffRefusal
```

วางไว้ในตัวกฎ ไม่ใช่ในแต่ละที่เรียก เพื่อไม่ให้มีการสะกดข้อยกเว้นนี้สองรอบ

### 6.3 จุดบังคับใช้ฝั่งเซิร์ฟเวอร์ — สามไฟล์

## 8. หน้าจอ

### 8.1 การตัดสินที่ขัดธรรมเนียมเดิม และผู้ใช้ยืนยันแล้ว

ผู้ใช้เลือก **ปุ่มยังอยู่ กดได้ แล้วขึ้นกล่องปฏิเสธ** โดยรู้ว่ามันสวนกับสิ่งที่
README §สิทธิ์ เขียนไว้:

> *"คิวถามคำถามเดียวกัน แถวแบบนี้จึงแสดงเหตุผลแทนที่จะแสดงปุ่มสองปุ่มที่กดแล้วได้
> 409"*

**และมีเส้นแบ่งที่ทำให้ทั้งสองอยู่ด้วยกันได้** ประโยคนั้นเขียนขึ้นสำหรับ *บทบาท* —
คนที่ไม่มีวันกดได้ไม่ควรเห็นปุ่ม เพราะปุ่มนั้นโกหกเรื่องตัวตนของเขา ส่วนข้อนี้เป็น
เรื่อง *เวลา* — คนคนเดียวกันกดได้เมื่อวาน กดไม่ได้วันนี้ ปุ่มที่หายไปเงียบ ๆ จะทำให้
เขาคิดว่าฟีเจอร์พัง ไม่ใช่ว่าตัวเองมาช้า **ปุ่มที่อธิบายตัวเองสอนกฎ ปุ่มที่หายไปซ่อนกฎ**
บรรทัดนี้ควรถูกเขียนลง README ตอนที่โค้ดลง ไม่ใช่ปล่อยให้สองที่ดูขัดกัน

### 8.2 รูปกล่อง — ใช้ของเดิมทั้งหมด

## 11. ลำดับงาน

1. `src/config/policy.js` — สองคีย์ พร้อมคอมเมนต์ว่าทำไมเป็น COSMETIC

8. `lib/policyInert.js` — กฎ inert ของคีย์ขั้นต่ำ
