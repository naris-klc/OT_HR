# แผน — งวดปิดเองเมื่อพ้นวันที่ 3 แล้วแก้ไข ยกเลิก และถอนใบไม่ได้

**สถานะ: ออกแบบเสร็จ ยังไม่เขียนโค้ด** · ตัดสินร่วมกับผู้ใช้ 2026-09-14

> **แก้มาสองรอบในวันเดียว** รอบแรกถอนข้อผ่อนสองข้อ (ขั้นต่ำนับจากวันยื่น · ยื่นทัน
> ถือว่าทัน) ด้วยคำสั่ง *"ห้ามยกเลิก และถอนใบ หลังวันที่ 3 ทั้งหมด"* · รอบสอง
> เปลี่ยนหน้าจอพนักงานเป็น **ปุ่มหาย ขึ้นประโยค `หมดเวลาแก้ไข`** และเพิ่ม `แก้ไข`
> เข้ามาในกฎ · เก็บไว้ให้รู้ว่าข้อผ่อนเคยถูกเสนอแล้วถูกปฏิเสธ ไม่ใช่ไม่เคยคิดถึง

โจทย์ตั้งต้น: *"การกด ยกเลิก/ถอนใบ ห้ามเกินวันที่ 3 ของทุกเดือน และตั้งค่าในหน้า
นโยบายได้"*

**ในระบบนี้ ยกเลิก กับ ถอนใบ ไม่ใช่สิ่งเดียวกัน** แบ่งด้วยเส้น *ลายเซ็นแรก* —
ก่อนลายเซ็นคือ `ยกเลิก` (ใบตายทันที) หลังลายเซ็นคือ `ขอถอนใบ` (เป็นคำขอ รอคนตอบ)
ซึ่งแยกอีกเป็น *ขอ* กับ *ตัดสิน* · และ `แก้ไข` นั่งอยู่ก่อนเส้นเดียวกันคู่กับ
`ยกเลิก` มาตลอด **รวมสี่การกด ปิดด้วยเส้นเดียวกันทั้งหมด**

## 1. สิ่งที่ตกลงกันแล้ว

ถามผู้ใช้ห้ารอบ ทุกข้อมีคำตอบจากผู้ใช้ ไม่มีข้อไหนเดาเอง

| คำถาม | คำตอบ |
|---|---|
| ห้ามการกดอันไหน | **แก้ไข · ยกเลิก · ขอถอนใบ · ตัดสินคำขอถอน** (ใบของตัวเอง) |
| HR ถอนแถวที่ระบบสร้าง (`void`) ติดไหม | **ไม่ติด** |
| วันที่ 3 นับเทียบเดือนไหน | **เดือนถัดจากงวดของใบ** |
| ฝ่ายบุคคล / ผู้ดูแลระบบ ติดไหม | **ไม่ติด ข้ามได้เสมอ** |
| "ปิดงวด" ในโจทย์คืออะไร | **พ้นวันที่ 3 = งวดปิดเอง** ไม่ใช่ฟีเจอร์ ปิดงวด ที่ถูกถอนไป |
| คำขอที่ยื่นทัน แต่ตัดสินหลังวันตัด | ~~ยื่นทันถือว่าทัน~~ → **ปิดด้วย** |
| ใบย้อนหลังที่เกิดมาก็เลยวันตัดแล้ว | ~~ให้ขั้นต่ำนับจากวันยื่น~~ → **ตัดทิ้ง ยกเลิกเองไม่ได้เลย** |
| วันที่ 3 เอง ยังกดได้ไหม | **ได้ทั้งวัน** ปิดเที่ยงคืนขึ้นวันที่ 4 |
| ค่าที่ ship ไปกับโค้ด | **ไม่กำหนด** HR เปิดเอง |
| ตัวเลือกในดรอปดาวน์ | ไม่กำหนด · 1 · 2 · 3 · 5 · 7 · 10 · 15 |
| ปุ่มของ **พนักงาน** เมื่อเลยกำหนด | ~~ปุ่มอยู่ กดแล้วขึ้นกล่องปฏิเสธ~~ → **ปุ่มหาย ขึ้นประโยคแทน** |
| ประโยคนั้นเขียนว่าอะไร | **`หมดเวลาแก้ไข`** |
| `แก้ไข` ติดกฎนี้ไหม | **ติด** |
| ปุ่มใน **คิวคำขอถอน** ของหัวหน้า | ~~ปุ่มหาย ขึ้นเหตุผลแทน~~ → **ปุ่มคู่เทา กดไม่ได้ พร้อมเหตุผล** |
| HR ลงมือหลังวันตัด เตือนไหม | **เตือน** — แถบในฟอร์ม **และ** กล่องยืนยัน ทั้งสองอย่าง |
| เตือนตอน HR ทำอะไรบ้าง | **แก้ไข + ตัดสินคำขอถอน** ไม่รวม `void` |
| HR ตัดสินคำขอถอนหลังวันตัด ต้องกรอกเหตุผลไหม | **ต้องกรอก** — วันนี้ไม่บังคับ ดู §8.6 |

แถวที่ขีดฆ่าเก็บไว้เพราะเคยมีเหตุผลรองรับยาว ๆ และเหตุผลนั้นผิด ไม่ใช่แค่ถูกแทน

## 2. ไม่ใช่การเอา ปิดงวด กลับมา

**นี่คือกำแพงระดับเดือนตัวแรกที่กลับเข้าระบบ หลัง ปิดงวด ถูกถอนเมื่อ 2026-08-31**
และผู้ใช้เรียกมันด้วยชื่อนั้นเอง จึงต้องเขียนให้ชัดว่าอันไหนเป็นอันไหน

หัวไฟล์ `lib/periodStatus.js` บอกเหตุผลที่ HR ขอถอนไว้: **แฟ้มกระดาษ F-HR-027 ที่
เซ็นแล้วคือตัวบันทึกจริง** ล็อกซ้ำในฐานข้อมูลไม่ได้อะไร แถมไปขวางสิ่งที่ HR ทำบ่อย
ที่สุด คือกลับเข้าไปแก้แถวที่บัญชีทัก

| | ปิดงวด (ถอนไปแล้ว) | ข้อนี้ |
|---|---|---|
| ทางเขียนที่ถูกปฏิเสธ | **เก้า** รวมทางแก้ไขของ HR | **สี่** ของพนักงานกับผู้เซ็นล้วน ๆ |
| HR ติดไหม | ติด ต้องให้ผู้ดูแลระบบเปิดคืน | **ไม่ติดเลย** |
| ปิดเพราะอะไร | มีคนกดปุ่ม | **ปฏิทิน** ไม่มีปุ่ม |
| เก็บอะไรในฐานข้อมูล | `otPeriodLocks` + `closedPeriods` | **ไม่มีอะไรเลย** เลขคณิตจาก `workDate` |
| เปิดคืนยังไง | ผู้ดูแลระบบเปิดพร้อมเหตุผล | ไม่มีอะไรให้เปิด · HR ทำแทนได้เลย |
| ตอน deploy | ทุกเดือนถูกปิดตามที่เคยกด | **ไม่มีอะไรเปลี่ยน** ship มาเป็น ไม่กำหนด |

**แถวแรกเคยอ่านว่า สาม จนถึงรอบแก้ที่สอง** — เพิ่ม `แก้ไข` คือการเดินเข้าหา ปิดงวด
หนึ่งก้าว · ที่ยังต่างคือ **`แก้ไข` ที่ปิดเป็นของพนักงาน ไม่ใช่ของ HR**
(`editPermission` ถาม `mayCorrectEntries` เป็นสาขาแรก) ซึ่งเป็นทางเดียวที่ ปิดงวด
ปิดแล้ว HR บ่นจนต้องถอน · ถ้ามีคนเสนอให้ปิดทางของ HR ด้วย นั่นคือ ปิดงวด กลับมา
ต้องกลับไปคุยกับ HR ก่อน

**"งวดปิดเอง" เป็นคำบรรยาย ไม่ใช่สถานะ** ไม่มีที่ไหนเก็บว่างวดไหนปิดแล้ว มีแต่
ฟังก์ชันบริสุทธิ์ที่ตอบเมื่อถูกถาม

หัวไฟล์เดียวกันบอกที่ทางของกฎแบบนี้ไว้แล้ว และแผนนี้ทำตามตรงตัว (§6):

> *"if a future rule needs to STOP a write, it does not belong here — it belongs
> beside `editPermission`, with the other rules that say no."*

## 4. กฎ

### 4.1 นิยาม

ให้ `cancelCutoffDay` = D (1–15 หรือ `null`)

```
วันสุดท้ายของใบ = วันที่ D ของเดือนถัดจาก periodOf(entry.workDate)
```

**เท่านี้** ไม่มี `max()` ไม่มีขั้นต่ำ ไม่มีข้อยกเว้นรายใบ

- `null` → กฎไม่ทำงาน (ค่าที่ ship)
- `today() <= วันสุดท้าย` — **วันที่ D เองกดได้ทั้งวัน**
- ทุกวันเป็นสตริง `'YYYY-MM-DD'` จาก `today()` เท่านั้น

### 4.2 วัดที่ `today()` ทั้งสี่การกด

แก้ไข · ยกเลิก · ขอถอนใบ · ตัดสินคำขอถอน (ทั้งอนุมัติและไม่อนุมัติ)

ฉบับแรกให้ขั้นตัดสินวัดที่ `entry.withdrawal.requestedAt` **ถูกถอนตามคำสั่ง
"ทั้งหมด"** ผลที่ตามมาเป็นของจริง:

> **คำขอถอนใบที่ค้างข้ามวันตัด หัวหน้าตัดสินไม่ได้อีกเลย เหลือทางเดียวคือฝ่ายบุคคล**

และไปโผล่ที่ `periodItems` (`lib/periodStatus.js:118`) ซึ่งนับคำขอถอนที่ค้างเป็น
รายการค้างของเดือนนั้น — สรุปสถานะงวดเก่าจะไม่มีวันว่างเอง · ไม่ใช่บั๊ก แต่เป็นราคา
ของคำว่า *ทั้งหมด* และ §8.2 คือสิ่งที่ทำให้มันไม่เงียบ

### 4.3 ตัวอย่างเดินจริง (D = 3, วันนี้ 2026-09-14)

| ใบ | `workDate` | งวด | วันสุดท้าย | กดได้ไหม |
|---|---|---|---|---|
| ก | 2026-08-20 | 2026-08 | 2026-09-03 | **ไม่ได้** เลยมา 11 วัน |
| ข | 2026-09-12 | 2026-09 | 2026-10-03 | ได้ |
| ค | 2026-07-20 *(เพิ่งยื่นวันนี้)* | 2026-07 | 2026-08-03 | **ไม่ได้ตั้งแต่วินาทีที่ยื่น** |
| ง | 2026-12-28 | 2026-12 | 2027-01-03 | ข้ามปี — เลขคณิตต้องถูก |

- ใบ **ก** 09-03 กดได้ · 09-04 ปฏิเสธ — จุดที่ off-by-one จะโผล่
- ใบ **ค** คือผลของการตัดขั้นต่ำทิ้ง **ยืนยันแล้วว่าต้องการแบบนี้** · เกิดขึ้นได้จริง
  เพราะ `maxPastSubmissionDays` ยัง ship เป็น `null`
- ใบ **ง** D สูงสุด 15 จึงไม่ต้องคิดเรื่องเดือนสั้นหรือปีอธิกสุรทิน

### 4.4 ค่าที่อ่านไม่ออก = ปิด

D ที่ไม่ใช่จำนวนเต็ม 1–28 ถือว่า **ไม่กำหนด** ไม่ใช่ถือว่าเข้มที่สุด

ตรงกับ `maxPastSubmissionDays` ตรงข้ามกับ `maxAdvanceSubmissionDays` · เหตุผลตาม
`src/config/policy.js`: **กฎที่พังแล้วล็อกคนออกจากใบตัวเอง แย่กว่ากฎที่พังแล้ว
ไม่ทำงาน** และรอบนี้เดิมพันสูงขึ้นเพราะไม่มีขั้นต่ำคอยรับ

## 5. นโยบายข้อใหม่ — ข้อเดียว

### 5.1 คีย์

```js
// src/config/policy.js — เพิ่มใน DEFAULT_POLICY
cancelCutoffDay: null,   // 1–28 หรือ null (ไม่กำหนด) — วันที่ของเดือนถัดจากงวด
```

ฉบับแรกมีสองคีย์ `cancelCutoffGraceDays` **ถูกตัดทิ้งทั้งข้อ ไม่ใช่ ship เป็น 0** —
ปุ่มที่มีไว้เพื่อไม่ถูกใช้คือปุ่มที่ต้องอธิบายตลอดไป · อยากได้การผ่อนวันไหน ค่อยเติม
พร้อมเหตุผลของวันนั้น

### 5.2 จัดประเภท — COSMETIC

เข้า `COSMETIC_KEYS` (`lib/policyVersion.js:70`) · `test/policyVersion.test.js:277`
บังคับอยู่แล้วว่าทุกคีย์ต้องอยู่ลิสต์ใดลิสต์หนึ่ง คอมมิตที่ลืมจะถูกจับเอง

เหตุผลแรงกว่าฝาแฝด (`maxAdvanceSubmissionDays` / `maxPastSubmissionDays`) ด้วยซ้ำ:
กฎนี้ไม่ถูกส่งเข้า `computeSession` เลย ไม่มีค่าไหนต่างไปแม้แต่นาทีเดียว มันตัดสิน
แค่ว่า *ปุ่มกดได้ไหม* · **และ replay ทำไม่ได้แม้จะอยากทำ** เพราะกฎถามว่าวันนี้เป็น
วันอะไร ส่วน replay รันในวันที่ขยับไปแล้วเสมอ

**ไม่ต้องแตะ `lib/policyInert.js`** — เหลือคีย์เดียว ไม่มีคีย์ไหนตัดหน้าใคร

## 6. ที่ทางของกฎในโค้ด

อยู่ใน `lib/entries.js` ข้าง `cancelPermission` ตามที่หัวไฟล์ `lib/periodStatus.js`
สั่งไว้ · **บริสุทธิ์ ไม่อ่านฐานข้อมูล** ให้เทสต์เรียกตรง ๆ และคอมโพเนนต์ import ได้
— เทสต์คอมโพเนนต์ที่นี่อ่าน *ข้อความในไฟล์* ไม่มี JSX transform กฎจึงห้ามอยู่ใน
คอมโพเนนต์

```js
/** วันสุดท้ายที่ใบนี้ยังแก้/ยกเลิก/ถอนได้ — 'YYYY-MM-DD' หรือ null */
export function cancelDeadline(entry, policy = {}) { … }

/** เลยวันตัดแล้วหรือยัง — ไม่สนใจว่าใครถาม · หน้าจอ HR ใช้ตัวนี้ ดู §8.6 */
export function isPastCancelCutoff(entry, policy = {}, onDate = today()) { … }

/** ปฏิเสธหรือไม่ เมื่อวัดที่วัน onDate — { status, error, short } หรือ null */
export function cancelCutoffRefusal(user, entry, policy = {}, onDate = today()) { … }
```

รับ `user` เป็นตัวแรก **เพื่อให้การปล่อย HR อยู่ในตัวกฎ** ไม่ใช่ให้แต่ละที่จำเอง:

```js
if (mayCorrectEntries(user)) return null;   // บรรทัดแรกของฟังก์ชัน
```

สะกดข้อยกเว้นที่เดียว สี่ทางเรียกกับสองหน้าจอจึงตีความต่างกันไม่ได้

### 6.1 เสียบเข้ากฎเดิมโดยไม่ทำของเก่าพัง

```js
editPermission(user, entry, note = '', { policy, on } = {})
cancelPermission(user, entry, { policy, on } = {})
withdrawEligibility(user, entry, { policy, on } = {})
```

`editPermission` มี `note` เป็นตัวที่สามอยู่แล้ว ออบเจกต์ใหม่จึงไปเป็นตัวที่สี่
ไม่แทรกกลาง — ผู้เรียกเดียวคือ `app/api/entries/[id]/route.js:44`

ไม่ส่ง `policy` = ไม่มีวันตัด = พฤติกรรมเดิมเป๊ะ **เทสต์เดิม 12 + 26 เคสผ่านต่อ
โดยไม่ต้องแตะ** ซึ่งเป็นสิ่งที่ต้องการ เพราะเคสพวกนั้นตรึงกฎที่ไม่ได้กำลังเปลี่ยน

`withdrawDecisionPermission` รับ `{ user, entry, delegations, today, verb }` อยู่แล้ว
เติม **`policy` กับ `note`** เข้าไป — `note` เพื่อบังคับเหตุผลเมื่อเลยวันตัด (§8.6)
แบบเดียวกับที่ `editPermission` รับ `note` เป็นพารามิเตอร์ของตัวเอง

### 6.2 ลำดับการตรวจ — วางตรงที่ข้อความเดิมจะส่งคนไปหาปุ่มที่ตายแล้ว

ไม่มีตำแหน่งมาตรฐานตำแหน่งเดียว และการพยายามให้มีคือที่มาของข้อความผิดเคส ·
**เกณฑ์: ข้อความปฏิเสธเดิมยังเป็นคำแนะนำที่ทำตามได้อยู่ไหม** ถ้าได้อย่าไปทับ

| ฟังก์ชัน | วางที่ไหน | ข้อความเดิมส่งคนไปไหน |
|---|---|---|
| `editPermission` | **ท้ายสุด** ก่อน `return { ok: true, action: 'edit' }` | *"กด ส่งใหม่"* — **ยังกดได้จริง** อย่าทับ |
| `cancelPermission` | หลังตรวจเจ้าของ **ก่อน** `awaitingFirstSignature` | *"อนุมัติแล้ว ใช้ ขอถอนใบ"* — ปุ่มที่กฎนี้เพิ่งปิด |
| `withdrawEligibility` | แบบเดียวกับ `cancelPermission` | เหตุผลเดียวกัน |
| `withdrawDecisionPermission` | หลังตรวจว่ามีคำขอเปิด **ก่อน** ตรวจสิทธิ์แผนก | คนนอกแผนกต้องได้ 403 ตามเดิม |

**`editPermission` วางท้ายสุดได้ของแถมที่ §8.3 ต้องใช้** — กฎยิงเฉพาะตอนคำตอบเดิม
เป็น `ok: true` แปลว่า *"ถ้าไม่มีวันตัด ปุ่มนี้จะถูกวาด"* พอดี

ใน `cancelPermission` สาขา `mayCorrectEntries(user) && isUntouchedSystemFiling(entry)`
อยู่บนสุดอยู่แล้วและต้องอยู่ต่อไป

### 6.3 จุดบังคับใช้ฝั่งเซิร์ฟเวอร์ — สี่ไฟล์

| ไฟล์ | แก้อะไร |
|---|---|
| `app/api/entries/[id]/route.js:44` | **ใหม่** ส่ง policy เข้า `editPermission` เป็นตัวที่สี่ |
| `app/api/entries/[id]/cancel/route.js:31` | ส่งเข้า `cancelPermission` พร้อม `on: today()` |
| `app/api/entries/[id]/withdraw/route.js:28` | ผ่าน `withdrawRequestPermission` → `withdrawEligibility` |
| `app/api/entries/[id]/withdraw/decide/route.js:37` | route นี้เรียก `today()` อยู่แล้วที่บรรทัด 36 |

อ่าน **นโยบายที่ใช้อยู่ตอนนี้** ไม่ใช่ `versionForDate` ของงวดนั้น — คำถามคือ
"วันนี้กดได้ไหม" ไม่ใช่ "ตอนนั้นคิดเงินยังไง" ตรงกับที่ `maxPastSubmissionDays` ทำ

**`/cancel` รับใช้สองการกระทำ** — คืน `action: 'void'` ให้ HR บนแถวที่ระบบสร้าง
กำแพงแบบเหวี่ยงแหบน route นี้จะปิดทางออกทางเดียวของแถวพวกนั้น · การปล่อย HR ในตัวกฎ
ทำให้ถูกตั้งแต่ต้น แต่ต้องมีเทสต์ตรึง ไม่ใช่ปล่อยเป็นผลพลอยได้

### 8.6 เตือน HR ก่อนลงมือกับงวดที่ปิดแล้ว

**ผู้ใช้สั่งเพิ่ม 2026-09-14** HR ยังข้ามกฎได้เหมือนเดิม แต่ต้องรู้ตัวก่อน — ทุกวันนี้
HR กดผ่านไปโดยไม่มีอะไรบอกว่าใบนั้นอยู่ในงวดที่พนักงานแตะเองไม่ได้แล้ว

**ขอบเขต: `แก้ไข` กับ `ตัดสินคำขอถอน`** ไม่รวม `void` — `void` ไม่ใช่ใบของพนักงาน
และไม่ต้องกรอกเหตุผลอยู่แล้วโดยตั้งใจ (§7)

**เตือนสองชั้น** ผู้ใช้เลือก *ทั้งสองอย่าง*: แถบที่เห็นตั้งแต่เปิด **และ** กล่อง
ยืนยันก่อนลงมือ

| | แถบเตือน | กล่องยืนยัน |
|---|---|---|
| **แก้ไข** — `OtForm.jsx` โหมด `hrEdit` (`:139`) เข้าจาก `HrEntries.jsx:273` ที่เดียว | `<Alert kind="warn">` คู่กับ hint ของ HR ที่ `OtForm.jsx:876` | `ConfirmDialog` (`components/common.jsx:1870`) คั่นก่อน `บันทึก` |
| **ตัดสินคำขอถอน** — `WithdrawalRequests.jsx` | **บรรทัดเหตุผลใน §8.2 ทำหน้าที่นี้อยู่แล้ว** ไม่ต้องเพิ่มอะไร | `ConfirmDialog` ก่อนส่ง ทั้ง อนุมัติ และ ไม่อนุมัติ · **มีช่องเหตุผลบังคับกรอก** |

**ปุ่มรวม อนุมัติให้ถอนทั้งหมด ยืนยันครั้งเดียว บอกจำนวน** ไม่ใช่เด้งทีละแถว — กล่อง
บอกว่าในชุดนี้มีกี่ใบที่อยู่ในงวดที่ปิดแล้ว และ **เหตุผลที่กรอกครั้งเดียวถูกบันทึก
ลงทุกใบในชุดนั้น** (`decisionNote` เก็บรายใบอยู่แล้ว `lib/withdrawal.js:223`)

#### ทำไมฝั่งตัดสินต้องบังคับกรอกเหตุผล แต่ฝั่งแก้ไขไม่ต้องเพิ่ม

สองการกดนี้มีด่านไม่เท่ากันอยู่แล้ววันนี้ — สำรวจ 2026-09-14:

| การกด | เหตุผลบังคับไหม (วันนี้) | ที่ตรวจ |
|---|---|---|
| แก้ไข โดย HR | **บังคับ** | `editPermission` → 400 *กรุณาระบุเหตุผลการแก้ไข* |
| ขอถอนใบ (พนักงาน) | **บังคับ** | `withdrawRequestPermission` → 400 |
| แก้ไข โดยพนักงานเอง · ยกเลิก · `void` · **ตัดสินคำขอถอน** | ไม่บังคับ | `decisionNote` เป็น `undefined` ได้ |

**`แก้ไข` จึงมีบันทึกอยู่แล้วว่าทำไม** กล่องยืนยันเป็นด่านที่สองซ้อนของเดิม ·
**`ตัดสินคำขอถอน` ไม่มีอะไรเลย** — ถ้าไม่บังคับ จะไม่มีที่ไหนบันทึกว่าทำไม HR ถึง
ตัดสินใบของงวดที่ปิดไปแล้ว **ผู้ใช้สั่งให้บังคับ 2026-09-14**

บังคับ **เฉพาะเมื่อเลยวันตัด** ไม่ใช่ทุกใบ — ใบในงวดที่ยังเปิดอยู่ตัดสินได้เหมือนเดิม
ไม่มีด่านเพิ่ม

**เซิร์ฟเวอร์ต้องบังคับด้วย ไม่ใช่แค่หน้าจอ** ตามแบบที่ `editPermission` ทำอยู่ —
`withdrawDecisionPermission` รับ `note` เพิ่มเข้าไปในออบเจกต์เดิม แล้วคืน 400 เมื่อ
เลยวันตัดและไม่มีเหตุผล · เขียนกฎไว้ในหน้าจออย่างเดียวคือด่านที่ข้ามได้ด้วย `curl`

**`ConfirmDialog` วันนี้ยังไม่มี `confirmDisabled`** (`components/common.jsx:1870`
มีแค่ `busy`) ปุ่ม ตกลง จึงกดได้ทั้งที่ช่องยังว่าง · **เพิ่มพร็อพนั้นเข้าไปในชุดร่วม**
ตาม AGENTS.md — ไม่ใช่ไปประกอบกล่องเองจาก `Modal` ซึ่งเป็นความผิดพลาดที่กฎข้อนั้น
มีไว้กัน

#### กฎตัวที่หน้าจอ HR ต้องใช้ ไม่ใช่ตัวเดียวกับที่ปฏิเสธ

`cancelCutoffRefusal` คืน `null` ให้ HR ตั้งแต่บรรทัดแรก (§6) — **หน้าจอ HR จึงถาม
มันไม่ได้** ถามแล้วได้ `null` เท่ากับ "ไม่มีอะไร" ซึ่งเป็นคำตอบที่ผิดในที่นี้

แยกภาคเลขคณิตออกมาเป็นฟังก์ชันของตัวเอง แล้วให้ทั้งสองทางเรียกใช้ตัวเดียวกัน:

```js
/** ใบนี้เลยวันตัดแล้วหรือยัง — ไม่สนใจว่าใครถาม */
export function isPastCancelCutoff(entry, policy = {}, onDate = today()) { … }

export function cancelCutoffRefusal(user, entry, policy = {}, onDate = today()) {
  if (mayCorrectEntries(user)) return null;
  if (!isPastCancelCutoff(entry, policy, onDate)) return null;
  return { status: 409, error: …, short: 'หมดเวลาแก้ไข' };
}
```

**ห้ามให้คอมโพเนนต์คำนวณวันที่เอง** — `cancelDeadline` กับการเทียบ `today()` เขียน
ซ้ำในหน้าจอเมื่อไร เป็นจุดที่กฎสองชุดเริ่มไม่ตรงกันเมื่อนั้น

## 12. สิ่งที่ยังไม่ได้ตัดสิน

1. **ถ้อยคำที่ยังเปิด** — ร่างไว้แล้ว รอยืนยัน · ประโยคยาว: *"งวด ส.ค. 2569 ปิดไป
   แล้วเมื่อ 3 ก.ย. 2569 — แก้ไข ยกเลิก หรือถอนใบเองไม่ได้ ติดต่อฝ่ายบุคคลเพื่อ
   ดำเนินการแทน"* · บรรทัดในคิว: *"งวด ส.ค. 2569 ปิดแล้วเมื่อ 3 ก.ย. 2569 —
   ตัดสินได้เฉพาะฝ่ายบุคคล"* · `label` / `hint` ตาม §5.3
2. **ถ้อยคำในแถบเตือน กล่องยืนยัน และป้ายช่องเหตุผลของ HR** (§8.6) — ยังไม่ได้ร่าง

**ปิดไปแล้ว** ปุ่มของพนักงาน · `หมดเวลาแก้ไข` · `แก้ไข` อยู่ในกฎ · บล็อก 5 (§5.4) ·
ปุ่มในคิวเป็นปุ่มเทา (§8.2) · เตือน HR สองชั้น ขอบเขตแก้ไข+ตัดสิน และบังคับกรอก
เหตุผลตอนตัดสิน (§8.6)

## 13. สิ่งที่แผนนี้รู้ว่าจะเจ็บ

ข้อ 1–3 เป็นผลของคำว่า *ทั้งหมด* ข้อ 4–6 เป็นผลของรอบแก้ทีหลัง ไม่มีข้อไหนเป็น
ข้อบกพร่องของการออกแบบ

1. **คิวคำขอถอนจะสะสมแถวที่มีแต่ HR แตะได้** ทุกเดือนที่ผ่านวันตัดโดยมีคำขอค้าง ·
   §8.2 ทำให้ไม่เงียบ แต่ไม่ได้ทำให้หาย
2. **ใบที่ยื่นย้อนหลังข้ามเดือนต้องพึ่ง HR เสมอ** และ `maxPastSubmissionDays` เป็น
   `null` แปลว่ายื่นย้อนหลังได้ไม่จำกัด · ถ้าปริมาณเป็นปัญหา ทางแก้ที่ถูกที่สุดคือ
   ตั้ง `maxPastSubmissionDays` ไม่ใช่ผ่อนกฎนี้
3. **HR เป็นคอขวดของทุกการแก้หลังวันตัด** ซึ่งคือสิ่งที่ ปิดงวด ถูกถอนเพื่อ
   หลีกเลี่ยง — ต่างกันที่รอบนี้ HR เป็นคนที่ *ผ่านได้* ไม่ใช่คนที่ *ติด* ·
   รอบแก้ที่สองทำให้หนักขึ้น เพราะ `แก้ไข` ถูกใช้บ่อยกว่า `ยกเลิก` มาก
4. **`ส่งใหม่` ยังเปิด และจะยืนข้าง `หมดเวลาแก้ไข` ได้จริง** — แก้ใบเดือนที่แล้ว
   ไม่ได้ แต่ยื่นใบใหม่สำหรับวันเดียวกันได้ · ไม่ใช่ช่องโหว่ (ใบใหม่เดินผ่านการ
   อนุมัติทั้งสาย) แต่จะถูกถามแน่ตอนใช้จริง · ไม่อยากให้เป็นแบบนั้นก็ตั้ง
   `maxPastSubmissionDays` ไม่ใช่ไปปิด `refileState`
5. **กล่องยืนยันจะเด้งใส่ HR บ่อย** — ทุกครั้งที่แก้ใบของเดือนก่อน ซึ่งเป็นงานที่
   หัวไฟล์ `lib/periodStatus.js` บอกว่า HR ทำบ่อยที่สุด · **ผู้ใช้เลือก "ทั้งสอง
   อย่าง" ทั้งที่รู้ข้อนี้** ถ้าใช้จริงแล้วรำคาญ ทางลดที่ตรงจุดที่สุดคือตัดกล่อง
   ยืนยันฝั่ง `แก้ไข` ออก เหลือแถบเตือน ไม่ใช่ไปลดขอบเขตของกฎ
6. **`หมดเวลาแก้ไข` กับ `แก้ไขไม่ได้` ใกล้กันจนสับสนได้** — ของเราแปลว่า *งวดปิด*
   ของ `components/HrEntries.jsx:742` แปลว่า *ใบนี้จบแล้ว* · วันนี้ไม่ชนกันเพราะ HR
   ไม่ติดกฎนี้ **แต่นั่นเป็นเรื่องบังเอิญของสิทธิ์ ไม่ใช่ของการออกแบบ** ถ้าวันหนึ่ง
   มีจอที่เห็นทั้งคู่ ต้องกลับมาตั้งชื่อใหม่
