# แผน — งวดปิดเองเมื่อพ้นวันที่ 3 แล้วยกเลิกและถอนใบไม่ได้

**สถานะ: ออกแบบเสร็จ ยังไม่เขียนโค้ด** · ตัดสินร่วมกับผู้ใช้ 2026-09-14

> **ฉบับนี้เขียนทับฉบับแรกของวันเดียวกัน** ฉบับแรกมีข้อผ่อนสองข้อ — *ขั้นต่ำนับจาก
> วันที่ยื่น* กับ *ยื่นทันถือว่าทัน ตัดสินเมื่อไหร่ก็ได้* — ผู้ใช้สั่งถอนทั้งคู่ใน
> รอบแก้ ด้วยประโยค **"เมื่อปิดงวดแล้ว ห้ามยกเลิก และถอนใบ หลังวันที่ 3 ทั้งหมด"**
> · คำว่า *ทั้งหมด* คือสิ่งที่ลบสองข้อนั้น และเก็บไว้เพื่อให้รู้ว่ากฎนี้เคยถูก
> เสนอให้ผ่อนแล้วถูกปฏิเสธ ไม่ใช่ไม่เคยถูกคิดถึง

โจทย์ตั้งต้นคือ *"การกด ยกเลิก/ถอนใบ ห้ามไม่ให้เกินวันที่ 3 ของทุกเดือน และตั้งค่าใน
หน้านโยบายได้ด้วย"*

สิ่งแรกที่การสำรวจตอบกลับมา และยังเป็นโครงของแผนนี้ คือ **ในระบบนี้ ยกเลิก กับ
ถอนใบ ไม่ใช่ของสิ่งเดียวกัน** มันคือสองกลไกที่แบ่งกันด้วยเส้น *ลายเซ็นแรก* —
ก่อนลายเซ็นคือ `ยกเลิก` (ทำได้ทันที ใบตายเดี๋ยวนั้น) หลังลายเซ็นคือ `ขอถอนใบ`
(ยังไม่มีอะไรขยับ เป็นคำขอที่รอคนตอบ) และตัวหลังยังแยกเป็นสองจังหวะอีก คือ *ขอ*
กับ *ตัดสิน* **รวมเป็นสามการกด และวันนี้ทั้งสามถูกปิดด้วยเส้นเดียวกัน**

## 1. สิ่งที่ตกลงกันแล้ว

ถามผู้ใช้สี่รอบ 2026-09-14 ทุกข้อด้านล่างมีคำตอบจากผู้ใช้ ไม่มีข้อไหนเดาเอง

| คำถาม | คำตอบ |
|---|---|
| กฎนี้ห้ามการกดอันไหน | **ยกเลิกใบของตัวเอง · ขอถอนใบที่อนุมัติแล้ว · ตัดสินคำขอถอน** |
| HR ถอนแถวที่ระบบสร้าง (`void`) ติดด้วยไหม | **ไม่ติด** |
| วันที่ 3 นับเทียบกับเดือนไหน | **วันที่ 3 ของเดือนถัดจากงวดของใบ** |
| ฝ่ายบุคคล / ผู้ดูแลระบบ ติดกฎไหม | **ไม่ติด — ข้ามได้เสมอ** |
| “ปิดงวด” ในโจทย์คืออะไร | **พ้นวันที่ 3 = งวดปิดเอง ไม่มีอะไรให้กด** — ไม่ใช่ฟีเจอร์ ปิดงวด ที่ถูกถอนไป |
| คำขอที่ยื่นทัน แต่ตัดสินหลังวันตัด | ~~ยื่นทันถือว่าทัน~~ → **ปิดด้วย** |
| ใบที่ยื่นย้อนหลังจนเกิดมาก็เลยวันตัดแล้ว | ~~ให้เวลาขั้นต่ำนับจากวันยื่น~~ → **ตัดขั้นต่ำทิ้ง ยกเลิกเองไม่ได้เลย** |
| วันที่ 3 เอง ยังกดได้ไหม | **ยังกดได้ทั้งวัน** — ปิดตอนเที่ยงคืนขึ้นวันที่ 4 |
| ค่าตั้งต้นที่ ship ไปกับโค้ด | **ไม่กำหนด** แล้ว HR เป็นคนเปิดเอง |
| ตัวเลือกในดรอปดาวน์ | ไม่กำหนด · 1 · 2 · 3 · 5 · 7 · 10 · 15 |
| ปุ่มของ **พนักงาน** เมื่อเลยกำหนด | **ปุ่มยังอยู่ กดได้ แล้วขึ้นกล่องปฏิเสธ** |
| ปุ่มใน **คิวคำขอถอน** ของหัวหน้า | **แถวยังอยู่ ปุ่มหาย ขึ้นเหตุผลแทน** |

สองแถวสุดท้ายตอบต่างกันโดยตั้งใจ — ดู §8.1

## 2. ข้อตึงที่ต้องพูดก่อน — ปิดงวด เคยถูกถอนออกไปแล้ว

**นี่คือกำแพงระดับเดือนตัวแรกที่กลับเข้าระบบ หลัง ปิดงวด ถูกถอนเมื่อ 2026-08-31**
และรอบนี้ผู้ใช้เรียกมันด้วยชื่อนั้นเองว่า *"เมื่อปิดงวดแล้ว"* จึงยิ่งต้องเขียนให้ชัด
ว่าอันไหนเป็นอันไหน

หัวไฟล์ `lib/periodStatus.js` เขียนเหตุผลที่ HR ถอนมันไว้ตรง ๆ ว่า **แฟ้มกระดาษ
F-HR-027 ที่เซ็นแล้วคือตัวบันทึกจริง** ล็อกในฐานข้อมูลซ้อนอีกชั้นไม่ได้อะไร และมันไป
ขวางสิ่งที่ HR ทำบ่อยที่สุด คือกลับเข้าไปแก้แถวที่บัญชีทัก

**ข้อนี้ไม่ใช่การเอา ปิดงวด กลับมา และความต่างวัดได้เป็นข้อ ๆ:**

| | ปิดงวด (ถอนไปแล้ว) | ข้อนี้ |
|---|---|---|
| ทางเขียนที่ถูกปฏิเสธ | **เก้า** รวมทางแก้ไขของ HR | **สาม** และเป็นทางของพนักงานกับผู้เซ็นล้วน ๆ |
| HR ติดไหม | ติด ต้องให้ผู้ดูแลระบบเปิดคืนพร้อมเหตุผล | **ไม่ติดเลย ไม่ต้องขอใคร** |
| งวดปิดเพราะอะไร | มีคนกดปุ่ม | **ปฏิทิน** — ไม่มีปุ่ม ไม่มีคนกด |
| ต้องเก็บอะไรในฐานข้อมูล | โมเดล `otPeriodLocks` + ฟิลด์ `closedPeriods` | **ไม่มีอะไรเลย** — เป็นเลขคณิตจาก `workDate` |
| เปิดคืนยังไง | ผู้ดูแลระบบเปิดพร้อมเหตุผลบนบันทึก | ไม่มีอะไรให้เปิดคืน · HR ทำแทนได้ทันทีอยู่แล้ว |
| ตอน deploy เกิดอะไร | ทุกเดือนถูกปิดตามที่เคยกด | **ไม่มีอะไรเปลี่ยน** — ship มาเป็น ไม่กำหนด |

**"งวดปิดเอง" จึงเป็นคำบรรยาย ไม่ใช่สถานะ** ไม่มีที่ไหนในระบบที่เก็บว่า "งวดนี้ปิด
แล้ว" และไม่มีอะไรให้ query — มีแต่ฟังก์ชันบริสุทธิ์ที่ตอบว่า *ใบนี้เลยเส้นหรือยัง*
เมื่อถูกถาม · ถ้าวันหนึ่งมีคนอยากได้ปุ่ม ปิดงวด จริง ๆ กลับมา นั่นเป็นงานคนละอัน
และต้องกลับไปคุยกับ HR ที่เป็นคนขอให้ถอนมันออก

และหัวไฟล์เดียวกันนั้นบอกที่ทางของกฎแบบนี้ไว้ด้วย:

> *"if a future rule needs to STOP a write, it does not belong here — it belongs
> beside `editPermission`, with the other rules that say no."*

แผนนี้ทำตามนั้นตรงตัว — ดู §6

### ของที่คนมักคิดว่าใช่ แต่ไม่ใช่

- **`lib/periodStatus.js`** — ตั้งแต่ 2026-08-31 ทุกฟังก์ชันในนั้นคืน *คำบรรยาย*
  ไม่มีตัวไหนคืน `{ status, error }` เลย กฎที่ปฏิเสธได้ห้ามไปอยู่ในไฟล์นี้
- **`maxPastSubmissionDays`** — คุม `workDate` ตอน *ยื่น* ไม่ใช่ตอนยกเลิก และเป็น
  ระยะนับจากวันนี้ ไม่ใช่วันที่ของเดือน คนละกฎ คนละโค้ดพาธ
- **`filingOf(entry)`** — ฉบับแรกใช้มันหาวันที่ยื่นสำหรับขั้นต่ำ **ฉบับนี้ไม่ใช้แล้ว**
  เพราะขั้นต่ำถูกตัดทิ้ง · เขียนไว้กันคนกลับมาเติมโดยคิดว่าลืม
- **`PolicyVersion.effectiveFrom`** — เป็นวันที่ชุดกฎเริ่มใช้ ไม่ใช่วันตัดรายเดือน

## 4. กฎ — เขียนเป็นเลขคณิตให้ไม่มีที่ให้ตีความ

### 4.1 นิยาม

ให้ `cancelCutoffDay` = D (เลข 1–15 หรือ `null`)

```
วันสุดท้ายของใบ = วันที่ D ของเดือนถัดจาก periodOf(entry.workDate)
```

**เท่านี้** ไม่มี `max()` ไม่มีขั้นต่ำ ไม่มีข้อยกเว้นรายใบ

- D เป็น `null` → **ไม่มีวันสุดท้าย** กฎทั้งข้อไม่ทำงาน (ค่าที่ ship)
- เปรียบเทียบแบบ `today() <= วันสุดท้าย` — **วันที่ D เองยังกดได้ทั้งวัน**
  ปิดตอนเที่ยงคืนขึ้นวันถัดไป
- ทุกวันเป็นสตริง `'YYYY-MM-DD'` เวลาสำนักงาน ผลิตจาก `today()` เท่านั้น

### 4.2 วัดที่ `today()` ทั้งสามการกด

| การกด | วัดที่วันไหน |
|---|---|
| ยกเลิกใบของตัวเอง | `today()` |
| ขอถอนใบ | `today()` |
| ตัดสินคำขอถอน — อนุมัติ **และ** ไม่อนุมัติ | `today()` |

ฉบับแรกให้ขั้นตัดสินวัดที่ `entry.withdrawal.requestedAt` เพื่อให้คำขอที่ยื่นทัน
ยังตัดสินได้ **ถูกถอนตามคำสั่ง "ทั้งหมด"** ผลที่ตามมาคือของจริงและต้องพูดตรง ๆ:

> **คำขอถอนใบที่ค้างข้ามวันที่ 3 จะถูกแช่ไว้ หัวหน้าตัดสินไม่ได้อีกเลย ไม่ว่าจะ
> อนุมัติหรือไม่อนุมัติ — เหลือทางเดียวคือฝ่ายบุคคล**

และมันไปโผล่ที่อื่นด้วย: `periodItems` (`lib/periodStatus.js:118`) นับคำขอถอนที่ค้าง
เป็นรายการ *ค้างอยู่* ของเดือนนั้น — แถวพวกนี้จะค้างตลอดไปจนกว่า HR จะเข้ามาจัดการ
สรุปสถานะงวดของเดือนเก่าจึงไม่มีวันว่างเอง นี่ไม่ใช่บั๊ก แต่เป็นราคาของคำว่า
*ทั้งหมด* และ §8.2 คือสิ่งที่ทำให้มันไม่เงียบ

### 4.3 ตัวอย่างเดินจริง (D = 3, วันนี้ 2026-09-14)

| ใบ | `workDate` | งวด | วันสุดท้าย | วันนี้กดได้ไหม |
|---|---|---|---|---|
| ก | 2026-08-20 | 2026-08 | 2026-09-03 | **ไม่ได้** — เลยมา 11 วัน |
| ข | 2026-09-12 | 2026-09 | 2026-10-03 | ได้ |
| ค | 2026-07-20 *(เพิ่งยื่นวันนี้)* | 2026-07 | 2026-08-03 | **ไม่ได้เลยตั้งแต่วินาทีที่ยื่น** |
| ง | 2026-12-28 | 2026-12 | 2027-01-03 | (ข้ามปี — เลขคณิตต้องถูก) |

- ใบ **ก** วันที่ 2026-09-03 กดได้ · 2026-09-04 ปฏิเสธ — เคสที่ off-by-one จะโผล่
- ใบ **ค** คือผลของการตัดขั้นต่ำทิ้ง **ยืนยันแล้วว่าต้องการแบบนี้** ใบย้อนหลัง
  ข้ามเดือนต้องพึ่ง HR เสมอ · มันเอื้อมถึงได้จริงเพราะ `maxPastSubmissionDays`
  ยัง ship เป็น `null` คือยื่นย้อนหลังได้ไม่จำกัด
- ใบ **ง** D สูงสุด 15 จึงไม่ต้องคิดเรื่องเดือนสั้นหรือปีอธิกสุรทิน

### 4.4 ค่าที่อ่านไม่ออก = ปิด

D ที่ไม่ใช่จำนวนเต็ม 1–28 ให้ถือว่า **ไม่กำหนด** ไม่ใช่ให้ถือว่าเข้มที่สุด

ตรงข้ามกับ `maxAdvanceSubmissionDays` ที่ค่าเสียแล้วตกไปที่คำตอบเข้ม และตรงกับ
`maxPastSubmissionDays` ที่ตกไปที่ผ่อน — ด้วยเหตุผลเดียวกับที่ `src/config/policy.js`
ให้ไว้: กฎที่พังแล้วล็อกคนออกจากใบของตัวเองแย่กว่ากฎที่พังแล้วไม่ทำงาน และรอบนี้
เดิมพันสูงขึ้น เพราะไม่มีขั้นต่ำคอยรับอีกแล้ว

## 5. นโยบายข้อใหม่ — ข้อเดียว

### 5.1 คีย์

```js
// src/config/policy.js — เพิ่มใน DEFAULT_POLICY
cancelCutoffDay: null,   // 1–28 หรือ null (ไม่กำหนด) — วันที่ของเดือนถัดจากงวด
```

ปุ่มที่มีไว้เพื่อไม่ถูกใช้คือปุ่มที่ต้องอธิบายตลอดไป และคำสั่งคือ *ทั้งหมด*
ถ้าวันหนึ่งอยากได้การผ่อน ก็เติมคีย์ตอนนั้น พร้อมเหตุผลของวันนั้น

และห้ามอยู่ทั้งสอง — คอมมิตที่ลืมข้อนี้จะถูกเทสต์จับเอง

เหตุผลยกมาจากฝาแฝดที่ใกล้ที่สุดสองตัวคือ `maxAdvanceSubmissionDays` และ
`maxPastSubmissionDays` และมันแรงกว่าด้วยซ้ำ: กฎนี้ไม่ถูกส่งเข้า `computeSession`
เลย ไม่มี `segments` `buckets` หรือ `totals` ค่าไหนต่างไปแม้แต่นาทีเดียวไม่ว่าตั้ง
เป็นอะไร มันตัดสินแค่ว่า *ปุ่มกดได้ไหม*

และเหมือนฝาแฝดทั้งคู่ **การ replay ข้อนี้ทำไม่ได้แม้จะอยากทำ** — กฎถามว่าวันนี้
เป็นวันอะไร และ replay รันในวันที่ขยับไปแล้วเสมอ `savePolicy` replay เฉพาะคีย์เชิง
เลขคณิต การลงทะเบียนไว้ที่นี่จึงเป็นสิ่งที่กันไม่ให้มันถูกถาม

**ไม่ต้องมีกฎ inert** — ฉบับแรกต้องมี เพราะคีย์ขั้นต่ำจะตายเมื่อวันตัดเป็น `null`
เหลือคีย์เดียวแล้วไม่มีคีย์ไหนตัดหน้าใคร `lib/policyInert.js` ไม่ต้องแตะเลย

## 6. ที่ทางของกฎในโค้ด

ทั้งหมดอยู่ใน `lib/entries.js` ข้าง `cancelPermission` ตามที่หัวไฟล์
`lib/periodStatus.js` สั่งไว้ **บริสุทธิ์ ไม่อ่านฐานข้อมูล** ให้เทสต์เรียกได้ตรง ๆ
และให้คอมโพเนนต์ import ได้ (เทสต์คอมโพเนนต์ในโปรเจกต์นี้อ่าน *ข้อความในไฟล์*
ไม่มี JSX transform กฎจึงห้ามอยู่ในคอมโพเนนต์)

```js
/** วันสุดท้ายที่ใบนี้ยังยกเลิก/ถอนได้ — 'YYYY-MM-DD' หรือ null เมื่อไม่กำหนด */
export function cancelDeadline(entry, policy = {}) { … }

/** ปฏิเสธหรือไม่ เมื่อวัดที่วัน onDate — { status, error } หรือ null */
export function cancelCutoffRefusal(user, entry, policy = {}, onDate = today()) { … }
```

`cancelCutoffRefusal` รับ `user` เป็นตัวแรก **เพื่อให้การปล่อย HR อยู่ในตัวกฎ**
ไม่ใช่ให้แต่ละที่เรียกจำเอง:

```js
if (mayCorrectEntries(user)) return null;   // บรรทัดแรกของฟังก์ชัน
```

สะกดข้อยกเว้นนี้ที่เดียว — สามทางเรียกกับสองหน้าจอจึงไม่มีทางตีความต่างกัน

### 6.1 เสียบเข้ากฎที่มีอยู่ โดยไม่ทำของเก่าพัง

`cancelPermission` และ `withdrawEligibility` **รับพารามิเตอร์เพิ่มแบบมีค่าตั้งต้น**
ไม่เปลี่ยนลายเซ็นเดิม:

```js
cancelPermission(user, entry, { policy, on } = {})
withdrawEligibility(user, entry, { policy, on } = {})
```

ไม่ส่ง `policy` มา = ไม่มีวันตัด = พฤติกรรมเดิมทุกประการ **เทสต์เดิม 12 + 26 เคส
จึงผ่านต่อโดยไม่ต้องแตะ** ซึ่งเป็นสิ่งที่ต้องการ เพราะเคสพวกนั้นตรึงกฎที่ไม่ได้
กำลังเปลี่ยน

`withdrawDecisionPermission` โชคดีกว่าเพื่อน — มันรับ `{ user, entry, delegations,
today, verb }` อยู่แล้ว เติมแค่ `policy` เข้าไปในออบเจกต์เดิม

### 6.2 ลำดับการตรวจ

ใน `cancelPermission` สาขา `mayCorrectEntries(user) && isUntouchedSystemFiling(entry)`
อยู่บนสุดอยู่แล้ว และต้องอยู่ต่อไป · การตรวจวันตัดไปอยู่ **หลัง** การตรวจความเป็น
เจ้าของ และก่อนการตรวจ `awaitingFirstSignature`

เหตุผลที่วางก่อนการตรวจลายเซ็น: ใบที่เลยงวดแล้วควรได้ข้อความว่า *งวดปิดแล้ว* ไม่ใช่
*หัวหน้าอนุมัติแล้ว กด ขอถอนใบ สิ* ซึ่งจะส่งคนไปกดปุ่มที่ปฏิเสธเขาเหมือนกัน

ใน `withdrawDecisionPermission` วางไว้หลังการตรวจว่ามีคำขอเปิดอยู่ และก่อนการตรวจ
สิทธิ์แผนก — คนที่ไม่มีสิทธิ์ในแผนกนั้นควรได้ 403 ตามเดิม ไม่ใช่ได้ข้อความเรื่องงวด

### 6.3 จุดบังคับใช้ฝั่งเซิร์ฟเวอร์ — สามไฟล์

| ไฟล์ | แก้อะไร |
|---|---|
| `app/api/entries/[id]/cancel/route.js:31` | โหลด `Setting.effectivePolicy()` ส่งเข้า `cancelPermission` พร้อม `on: today()` |
| `app/api/entries/[id]/withdraw/route.js:28` | เหมือนกัน ผ่าน `withdrawRequestPermission` → `withdrawEligibility` |
| `app/api/entries/[id]/withdraw/decide/route.js:37` | เหมือนกัน · route นี้เรียก `today()` อยู่แล้วที่บรรทัด 36 ใช้ตัวเดิมได้เลย |

อ่าน **นโยบายที่ใช้อยู่ตอนนี้** ไม่ใช่ `versionForDate` ของงวดนั้น — เพราะคำถามคือ
"วันนี้กดได้ไหม" ไม่ใช่ "ตอนนั้นคิดเงินยังไง" ตรงกับที่ `maxPastSubmissionDays` ทำอยู่

**`/cancel` เป็น endpoint เดียวที่รับใช้สองการกระทำ** — `cancelPermission` คืน
`action: 'void'` ให้ HR บนแถวที่ระบบสร้าง กำแพงวันที่แบบเหวี่ยงแหบน route นี้จะปิด
ทางออกทางเดียวของแถวพวกนั้นไปด้วย · การปล่อย HR ในตัวกฎ (§6) ทำให้เรื่องนี้ถูก
ตั้งแต่ต้น แต่ต้องมีเทสต์ตรึงไว้ ไม่ใช่ปล่อยให้เป็นผลพลอยได้

## 8. หน้าจอ — สองที่ ตอบคนละแบบโดยตั้งใจ

### 8.1 ทำไมสองที่ไม่เหมือนกัน

README §สิทธิ์ เขียนไว้ว่า:

> *"คิวถามคำถามเดียวกัน แถวแบบนี้จึงแสดงเหตุผลแทนที่จะแสดงปุ่มสองปุ่มที่กดแล้วได้
> 409"*

**ประโยคนั้นพูดถึง “คิว” และแผนนี้ทำตามมันเป๊ะ ๆ ที่คิว** — คิวคำขอถอนใบจะเอาปุ่ม
ออกแล้วขึ้นเหตุผลแทน

**หน้าพนักงานตอบตรงกันข้าม และนั่นคือคำตอบของผู้ใช้ที่ยืนยันมาสองรอบ** เส้นแบ่ง
ที่ทำให้สองอย่างอยู่ด้วยกันได้:

| | คิวคำขอถอน | หน้าพนักงาน |
|---|---|---|
| แถวเป็นของใคร | คำขอ **ของคนอื่น** | ใบ **ของตัวเอง** |
| คนอ่านมาทำอะไร | กวาดคิวให้หมด ไม่ได้มาหาแถวใดแถวหนึ่ง | มาดูใบของตัวเองใบนั้นโดยเฉพาะ |
| ปุ่มที่หายไปอ่านว่าอะไร | *"แถวนี้ยังไม่ถึงตาฉัน"* — ถูก | *"ระบบพัง"* หรือ *"ฉันไม่มีสิทธิ์"* — ผิดทั้งคู่ |
| จึงควร | เอาปุ่มออก ขึ้นเหตุผล | เก็บปุ่มไว้ ให้มันอธิบายตัวเอง |

**ปุ่มที่อธิบายตัวเองสอนกฎ ปุ่มที่หายไปซ่อนกฎ** — ในคิวมีข้อความอื่นสอนอยู่แล้ว
บนใบของตัวเองไม่มี · บรรทัดนี้ต้องถูกเขียนลง README ตอนโค้ดลง ไม่ใช่ปล่อยให้สองที่

**หน้าจอคำนวณเองจาก `cancelDeadline` ไม่ต้องรอเซิร์ฟเวอร์** — `usePolicy()` มีคีย์

มีอยู่แล้ววันนี้ และแผนนี้ไม่ได้มาแก้มัน แค่ไม่เดินเข้าไป

### 8.4 ข้อความ

ทุกที่ใช้สามส่วนเดียวกัน **งวดไหน · ปิดเมื่อไหร่ · วันนี้วันไหน** แล้วตามด้วยทางออก
(ฝ่ายบุคคล) · `docs/design.md` §2 บอกว่า *คำเตือนที่ไม่มีทางแก้ในมือผู้อ่าน ไม่ใช่
คำเตือน เป็นคำบ่น* — บรรทัดทางออกจึงไม่ใช่ของแถม

ถ้อยคำต้องมีแหล่งเดียว ไม่ใช่สะกดสามรอบในสามไฟล์ — ให้ `cancelCutoffRefusal` คืน

วันที่แสดงเป็นรูปแบบไทยตามที่หน้าเหล่านั้นใช้อยู่ ไม่ใช่ `YYYY-MM-DD` ดิบ

## 13. สิ่งที่แผนนี้รู้ว่าจะเจ็บ

เขียนไว้ให้เห็นก่อน ไม่ใช่ให้ไปเจอเอาตอน HR ตั้งค่าแล้ว **ทั้งสามข้อเป็นผลของคำว่า
*ทั้งหมด* ไม่ใช่ข้อบกพร่องของการออกแบบ**

1. **คิวคำขอถอนจะสะสมแถวที่มีแต่ HR แตะได้** ทุกเดือนที่ผ่านวันที่ 3 ไปโดยมีคำขอ
   ค้าง · §8.2 ทำให้มันไม่เงียบ แต่ไม่ได้ทำให้มันหาย
2. **ใบที่ยื่นย้อนหลังข้ามเดือนต้องพึ่ง HR เสมอ** และวันนี้ `maxPastSubmissionDays`
   เป็น `null` แปลว่ายื่นย้อนหลังได้ไม่จำกัด สองข้อนี้ประกอบกันแล้วสร้างงานให้ HR
   เพิ่มแน่นอน · ถ้าปริมาณเป็นปัญหา ทางแก้ที่ถูกที่สุดคือตั้ง
   `maxPastSubmissionDays` ไม่ใช่ผ่อนกฎนี้
3. **HR กลายเป็นคอขวดของทุกการแก้หลังวันที่ 3** ซึ่งคือสิ่งที่ ปิดงวด ถูกถอนออกไป
   เพื่อหลีกเลี่ยง — ต่างกันที่รอบนี้ HR เป็นคนที่ *ผ่านได้* ไม่ใช่คนที่ *ติด*
