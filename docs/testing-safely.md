## ไฟล์นี้พูดถึงเครื่องไหน

**เครื่อง Linux ที่รันแอปเป็นคอนเทนเนอร์** — เครื่องเดียวกับที่
[docs/docker.md](docker.md) บรรยาย **ไม่ใช่**แล็ปท็อป Windows ที่ README §Status
กับ [docs/network.md](network.md) พูดถึง วิธีทดสอบของสองเครื่องนี้ไม่เหมือนกัน
และความต่างข้อแรกคือข้อที่ทำให้คนทำผิดเยอะที่สุด:

| | แล็ปท็อป Windows | เครื่อง Linux (ไฟล์นี้) |
|---|---|---|
| อะไรเสิร์ฟ `:3000` | `next start` อ่าน `.next` ที่รากของ repo | คอนเทนเนอร์ `primus-ot` อ่าน `.next` ที่อยู่**ในอิมเมจ** |
| `npm run build` ทำอะไรกับของที่ใช้อยู่ | **ทำแอปล่ม** — ต้องเลี่ยงด้วย `VERIFY_DIST_DIR` | ไม่กระทบเลย — คนละสำเนากัน |
| build คือ deploy ไหม | **ใช่** เป็นการกระทำเดียวกัน | **ไม่ใช่** — build เกิดในอิมเมจ ตัวเก่ายังเสิร์ฟอยู่ |
| deploy คือคำสั่งอะไร | `scripts/deploy.ps1` | `docker compose up -d --build` |

**`VERIFY_DIST_DIR` จึงไม่ใช่กติกาของเครื่องนี้** — บนเครื่องนี้เขียน `.next/`
ทับกี่ครั้งก็ได้ คอนเทนเนอร์ไม่ได้อ่านมัน และ `.dockerignore` ก็ตัด `.next/`
ออกจาก build context อยู่แล้ว (ห้ามตั้ง `VERIFY_DIST_DIR` ในอิมเมจ ด้วยเหตุผล
ที่เขียนไว้หัว `Dockerfile`)

## ชั้นที่ 1 — `npm test` ปลอดภัยเต็มที่

ชุดเทสต์ทั้งชุดใน [test/](../test/) **ไม่ต่อฐานข้อมูลเลย** ไม่ต้องมี `mongod`
ไม่ต้องมี `.env` และรันได้แม้ตอนคนกำลังใช้งานอยู่

ไม่ใช่การเดาจากชื่อไฟล์ — [test/seedEntryPoint.test.js](../test/seedEntryPoint.test.js)
บังคับข้อนี้ไว้เป็นเทสต์: มันชี้ `MONGODB_URI` ไปที่พอร์ตที่ต่อไม่ติด สลับ
`mongoose.connect` เป็นตัวปลอม แล้ว assert ว่า `readyState` ยังเป็น 0 หลัง import
ทุกไฟล์ — ด่านนี้มีไว้จับกรณีที่ import ไฟล์เดียวแล้วมีการต่อฐานข้อมูลเกิดขึ้นเอง

```bash
npm test
```

**"ปลอดภัย" ไม่ได้แปลว่า "เขียว" — และเรื่องนี้เพิ่งกัดจริงเมื่อ 2026-09-09**
ชุดเทสต์ตก 31 เคสบนเครื่องนี้ ทั้งที่ tree สะอาดและโค้ดไม่มีอะไรผิดเลย: เทสต์
เรื่องเลย์เอาต์แปดไฟล์ค้นข้อความใน `app/styles.css` ด้วยสตริงที่สะกดด้วย `\r\n`
ซึ่งเป็นจริงเฉพาะบน checkout ของแล็ปท็อป — `core.autocrlf` เปิดอยู่ที่นั่น ไฟล์ใน
working tree จึงเป็น CRLF ส่วนเครื่องนี้ checkout คอมมิตเดียวกันได้ LF **แก้แล้ว
โดยให้เทสต์ normalise บรรทัดก่อนเทียบ** ซึ่งเป็นท่าที่ `test/adminApproval.test.js`
ทำถูกอยู่ก่อนแล้ว · เจออาการ "ตกเป็นพวงทั้งที่ไม่ได้แก้อะไร" เมื่อไหร่ ให้สงสัย
ข้อนี้ก่อนเสมอ — เหตุผลเต็มอยู่ในหัวคอมเมนต์ของ `.gitattributes`

**แล้วมันกลับมาอีกเย็นวันเดียวกัน สลับข้าง** — [test/manualScreen.test.js](../test/manualScreen.test.js)
ที่เข้ามาพร้อมคู่มือหน้าเดียวอ่านซอร์สด้วย `readFileSync` ตรง ๆ ไม่ normalise และ
assertion ของมันสะกดด้วย `\n` จึง**ผ่านบน checkout แบบ LF และตก 5 เคสบน CRLF**
คือกลับทางกับ 31 เคสข้างบนเป๊ะ ๆ (`SECTIONS` แจงได้ 0 section ไฟล์นั้นจึงไม่ได้
ตรวจอะไรเลย) แก้ที่ `read` ของไฟล์นั้นเมื่อ 2026-09-10 · บทเรียนไม่ใช่ว่าเทสต์แปด
ไฟล์นั้นแก้แล้ว แต่คือ**กฎนี้ไม่ปิดตัวเองเมื่อมีไฟล์เทสต์ใหม่เข้ามา** เทสต์ที่ grep
ซอร์สต้อง normalise บรรทัดตั้งแต่วันที่เขียน ไม่ใช่ตอนที่มีคนไป checkout อีกแบบ
แล้วเจอ — ซึ่งรอบนี้คือแล็ปท็อป Windows เครื่องใหม่ที่เพิ่งลง dependency

## ชั้นที่ 2 — แยกฐานข้อมูลก่อนทำอย่างอื่น

สร้างไฟล์ `.env.development.local` ที่รากของ repo:

```
MONGODB_URI=mongodb://127.0.0.1:27017/primus_ot_dev
JWT_SECRET=<สุ่มใหม่ ยาว ๆ คนละตัวกับของจริง>
```

**ทำไมชื่อนี้** — Next โหลดไฟล์ env ตามลำดับ `process.env` → `.env.$(NODE_ENV).local`
→ `.env.local` → `.env.$(NODE_ENV)` → `.env` แล้ว**หยุดที่ตัวแรกที่เจอ**
(`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md`
§Environment Variable Load Order) ชื่อนี้จึงชนะ `.env` เฉพาะตอน `next dev` และ
**คอนเทนเนอร์ไม่มีวันอ่านมัน** เพราะ compose ส่งให้เฉพาะ `.env` ผ่าน `env_file:`
และตัวมันรันด้วย `NODE_ENV=production` ทั้งสองทางเป็นคนละไฟล์กันโดยโครงสร้าง
ไม่ใช่โดยวินัยของคนพิมพ์คำสั่ง

**ทำไม `JWT_SECRET` ต้องคนละตัว** — ไม่ใช่พิธีกรรม มันทำให้คุกกี้ของฝั่งทดสอบ
ใช้กับของจริงไม่ได้และกลับกัน เปิดสองแท็บพร้อมกันก็ไม่มีทางที่ session จะข้ามฝั่ง

**ทั้งสองไฟล์ไม่หลุดที่ไหน** — `.gitignore` และ `.dockerignore` คลุม `.env.*`
ทั้งคู่มาตั้งแต่ 2026-09-09 (เหตุผลเต็มเขียนไว้ในสองไฟล์นั้น: ความลับที่เข้าไป
อยู่ในเลเยอร์ของอิมเมจหรือใน history ของ git ลบทีหลังไม่ได้จริง)

### 🔴 สคริปต์ใน `src/` ไม่ได้เล่นตามกติกานี้

`next dev` เท่านั้นที่รู้จัก `.env.development.local` — สคริปต์ดูแลระบบทุกตัว
(`npm run seed`, `backup`, `restore`, `whatif`, `migrate:*`, `reset-admin`)
ใช้ `import 'dotenv/config'` ตรง ๆ ซึ่ง **อ่าน `.env` ไฟล์เดียว = ฐานจริง**

เวลารันสคริปต์กับฐานทดสอบต้องใส่ค่าหน้าบรรทัดทุกครั้ง — ใช้ได้เพราะ dotenv
ไม่ทับค่าที่ตั้งมาแล้วใน environment ตัวแปรหน้าบรรทัดจึงชนะ `.env` เสมอ:

```bash
MONGODB_URI=mongodb://127.0.0.1:27017/primus_ot_dev npm run seed
```

### เอาข้อมูลจริงมาลงฐานทดสอบ

`--to` ของ [src/restore.js](../src/restore.js) มีไว้เพื่อการนี้โดยตรง:

```bash
npm run backup                                    # ลง ./backups/primus_ot-<วันเวลา>/
npm run restore -- ./backups/primus_ot-<วันเวลา> \
  --to mongodb://127.0.0.1:27017/primus_ot_dev --yes
```

⚠ สำเนานั้นคือฐานข้อมูลทั้งก้อน มี `passwordHash` ของทุกบัญชีและ `birthDate` ของ
พนักงานทุกคน — ฟิลด์ที่แอปตั้งใจซ่อนจากหัวหน้างาน **ฐาน `primus_ot_dev` จึงต้อง
ถูกดูแลเท่ากับฐานจริง** ไม่ใช่ "ข้อมูลเล่น" และมันอยู่บน `mongod` ตัวเดียวกัน
บนดิสก์เดียวกัน · อีกทางคือ `npm run seed` ซึ่งได้ข้อมูลสาธิตล้วน ไม่มีคนจริง

## ชั้นที่ 3 — dev server สำหรับงาน frontend

`npm run dev` ตรึง `-p 3000` ไว้ ซึ่งจะไปชนคอนเทนเนอร์ ใช้พอร์ตอื่นแทน:

```bash
npx next dev -p 3001
```

🔴 **ถ้าจะเปิดจากมือถือหรือเครื่องอื่นใน LAN ต้องแก้ `next.config.js` ก่อน** —
`allowedDevOrigins` มีแค่ `192.168.109.*` กับ `172.16.4.*` ซึ่งเป็นซับเน็ตของ
แล็ปท็อป Windows เครื่องนี้อยู่ที่ `192.168.100.17` **ยังไม่มีบรรทัดที่ตรง** และ
อาการเวลาไม่ตรงคือ Next ตอบ 403 ให้ `/_next/*` ทุกก้อน หน้าเว็บขึ้นแต่ไม่มีสไตล์
ไม่ใช่ error ที่อ่านออกทันที · เติม `'192.168.100.*'` เข้าไปในลิสต์นั้น — เป็น
ค่าที่มีผลเฉพาะ dev server ไม่แตะพฤติกรรมของอิมเมจ

## ชั้นที่ 4 — ทดสอบ "ของที่จะ deploy จริง" คู่ขนานไปกับของจริง

`next dev` ซ่อนบั๊กทั้งคลาสที่โผล่เฉพาะตอน `next build` — เรื่องนี้เคยเกิดจริง
และกลายเป็น [test/delegationQueryBinding.test.js](../test/delegationQueryBinding.test.js)
ก่อน deploy จึงควรเดินอิมเมจจริงหนึ่งรอบ **โดยไม่ใช่การ deploy**

```bash
docker build -t primus-ot:test .
docker run -d --name primus-ot-test --network host \
  --env-file .env.dev \
  -e NODE_ENV=production -e TZ=Asia/Bangkok -e OT_TIMEZONE=Asia/Bangkok \
  primus-ot:test npx next start -p 3010

curl -s localhost:3010/api/health          # ต้องได้ 200 และ database.ok: true
docker logs -f primus-ot-test
docker rm -f primus-ot-test                # เลิกแล้วเก็บกวาด
```

สามบรรทัดที่ต้องเข้าใจ ไม่ใช่ก๊อป:

- **`docker build` + `docker run` ไม่ใช่ `docker compose up`** — compose จะสลับ
  คอนเทนเนอร์จริงและทับ tag `primus-ot:latest` นั่นคือ deploy tag `:test`
  ทำให้อิมเมจของจริงยังอยู่ให้ถอยกลับได้
- **ต้อง override คำสั่งท้ายบรรทัดเป็น `-p 3010`** เพราะ `start` ใน `package.json`
  ตรึง `-p 3000` ไว้และ `-p` ชนะ `$PORT` เสมอ · ภายใต้ `--network host` ไม่มี
  port mapping ให้ remap ด้วย ตั้งพอร์ตที่ตัวโปรแกรมจึงเป็นทางเดียว
- **`--env-file` ของ `docker run` ไม่รู้จัก `.env.development.local`** ต้องมี
  `.env.dev` อีกใบที่มีครบทั้ง `MONGODB_URI` `JWT_SECRET` `JWT_TTL` ไม่งั้น
  `instrumentation-node.js` จะ exit 1 ทันทีที่ start พร้อมบอกว่าขาดตัวไหน
  (`.env.*` ถูก ignore อยู่แล้วทั้งใน git และ build context)

พอร์ต 3010 ไม่ออกอินเทอร์เน็ต เพราะอุโมงค์ชี้ที่ 3000 — แต่ `--network host`
แปลว่ามัน**เปิดทุก interface ใน LAN** อย่าทิ้งค้างไว้ข้ามคืน

## เส้นแดง — คำสั่งที่แตะของจริงทันที

| คำสั่ง | เกิดอะไรขึ้น |
|---|---|
| `docker compose up -d --build` · `down` · `restart` | **คือการ deploy / การดับของจริง** ไม่ใช่การลอง |
| `npm run seed` ที่ไม่มี `MONGODB_URI=` นำหน้า | `deleteMany({})` ห้า collection บนฐาน HR จริง |
| `npm run restore` ที่ลืม `--to` | เขียนทับฐานจริงทั้งก้อน |
| `docker rm -f primus-ot` | ตัวจริงชื่อนี้ ตัวทดสอบต้องตั้งชื่อให้ต่างชัด ๆ |

เรื่อง `npm run seed` มีตาข่ายรับอยู่ชั้นหนึ่ง — `seedSafety()` ใน
[lib/seedGuard.js](../lib/seedGuard.js) นับว่ามีอะไรในฐานที่ seed ไม่ได้ใส่ไว้เอง
บ้าง (พนักงานนอกรายชื่อสาธิต ใบ OT ที่ยื่นจริง ประวัติแก้ทะเบียน เวอร์ชันนโยบาย
ผู้รับช่วงอนุมัติ) แล้วปฏิเสธพร้อมบอกว่าเจออะไร **แต่มันเป็นตาข่าย ไม่ใช่ประตูล็อก**
— `--force` เดินผ่านมันได้ และคำเตือนที่มันพิมพ์ออกมาก็ระบุเองว่าสิ่งที่ถูกลบ
ห้า collection นั้น "ไม่ได้คืนฐานข้อมูลกลับไปเป็นสภาพสะอาด" เพราะ audit trail
กับ policy version ไม่ถูกลบตามและจะชี้ไปที่แถวที่ไม่มีอยู่แล้ว

## จังหวะการทำงานที่แนะนำ

1. `git switch -c <ชื่องาน>` — อย่าทำงานบน `main` ที่เป็นตัวที่ deploy
2. แก้โค้ด → `npx next dev -p 3001` (ชี้ฐาน `primus_ot_dev`)
3. `npm test`
4. `docker build -t primus-ot:test .` แล้วเดินจริงที่ `:3010`
5. ตามกติกาใน [AGENTS.md](../AGENTS.md): grep เอกสารหาสิ่งที่เพิ่งเปลี่ยน แล้วแก้
   ให้อยู่ใน commit เดียวกัน
6. merge เข้า `main`
7. **`docker compose up -d --build` — ขั้นนี้คนเป็นคนสั่ง** ไม่ใช่ขั้นตอนที่ใคร
   ทำแถมมาระหว่างทางเพื่อ "ตรวจว่าคอมไพล์ผ่าน"

## ที่ยังไม่ได้เดินจริง
