# แผน — ฝ่ายบุคคลยกเลิกใบได้ พร้อมเหตุผล และ `void` ถูกถอนถาวร

**สถานะ: ทำเสร็จแล้ว 2026-09-15** · ออกแบบและตัดสินร่วมกับผู้ใช้วันเดียวกัน ·
`npm test` 2779/2779 · **เหลือการเดินบนแอปจริงที่ล็อกอินแล้ว** ซึ่งต้องใช้รหัสผ่าน
จริงบนฐานของฝ่ายบุคคล — เป็นคำสั่งของผู้ใช้ ไม่ใช่ขั้นตอนที่หยิบทำเอง

> **สามข้อที่ผู้ใช้สั่งเพิ่มหลังอ่านแผนรอบแรก**
>
> 1. **`void` ทิ้งถาวร** ไม่ใช่แค่ไม่แตะ — *"เคลียร์ฟีเจอร์ void ตายไปแล้วทิ้ง
>    ถาวรครับ ตกลงกันไปแล้วว่า ot วันเกิด จะต้องคีย์ตามปกติเหมือน ot วันอื่น ๆ
>    แตกต่างแค่มีการแสดงป้ายระบุว่าเป็น ot วันเกิด"* · คำถามข้อ 4 ที่ถามไปว่า
>    เหตุผลบังคับควรครอบ `void` ไหม จึงกลายเป็นคำถามที่ไม่มีอยู่จริง
> 2. **ปุ่มบน ตรวจสอบประจำเดือน ใช้คำว่า `ยกเลิก`** ไม่ใช่ `ยกเลิกใบ`
> 3. **ปุ่มปิดฟอร์มเปลี่ยนเป็น `ย้อนกลับ` แล้วยก `ยกเลิก` ให้การยกเลิกจริง ๆ ·
>    ชิดขวาทั้งหมด** — แผนรอบแรกวางปุ่มแดงไว้ชิดซ้ายแยกฝั่ง ซึ่งถูกปฏิเสธ
>
> และสองข้อที่ถามต่อจากนั้น: `ย้อนกลับ` ใช้**ทุกจอ**ที่ใช้ฟอร์มนี้ (ไม่ใช่เฉพาะจอ
> HR) · ลำดับปุ่มคือ **`ยกเลิก` · `ย้อนกลับ` · `บันทึกการแก้ไข`**

โจทย์ตั้งต้นมาจากคำถามของผู้ใช้ว่า *"ที่ hr อนุมัติไปแล้ว ขอยกเลิก/แก้ไข ได้หรือไม่"*
คำตอบที่อ่านออกมาจากโค้ดคือ **แก้ไขได้ ยกเลิกไม่ได้ และไม่มีใครยกเลิกได้เลย**

## 1. ช่องที่กำลังปิด

ใบที่ `approved` แล้ว งวดปิดแล้ว และยังไม่เคยมีใครยื่นคำขอถอน —
**ไม่มีใครเอาออกจากบัญชีได้อีก รวมทั้งฝ่ายบุคคล** เพราะทางออกทั้งสามปิดพร้อมกัน

| ทาง | ทำไมปิด |
|---|---|
| `ขอถอนใบ` | `withdrawEligibility` เปิดให้**เจ้าของใบเท่านั้น** และวันตัดปิดเจ้าของใบไปแล้ว · HR ยื่นแทนไม่ได้ ไม่มีทางในโค้ด |
| `ยกเลิก` | `cancelPermission` ต้องเป็นเจ้าของใบ · HR ได้เฉพาะแถวที่*ระบบ*สร้าง (`void`) |
| `ไม่อนุมัติ` | `approvalPermission` รับเฉพาะ `pending_mgr` / `pending_hr` · ใบ `approved` ตอบ 409 |

เหลือ `แก้ไข` ของ HR ซึ่ง**ลดชั่วโมงได้ แต่ทำให้เป็นศูนย์ไม่ได้** (`noOtHoursMessage`
ปฏิเสธใบ 0 ชม.) ชั่วโมงจึงค้างในยอดเดือนนั้นถาวร

**นับจากฐานจริงวันที่ออกแบบ:** 431 ใบ · `approved` 333 · `pending_mgr` 85 ·
`pending_hr` 1 — **419 ใบที่ยังมีชีวิตและไม่มีทางออกสักใบ**

§13 ของ [plan-cancel-cutoff-day.md](plan-cancel-cutoff-day.md) เขียนราคาของวันตัดไว้
สามข้อ แต่ไม่มีข้อนี้ — ตอนนั้นมองว่า *"เหลือทางเดียวคือฝ่ายบุคคล"* ซึ่งจริงสำหรับ
**แก้ไข** แต่ไม่จริงสำหรับ **เอาใบออก** เพราะ HR ไม่เคยมีปุ่มนั้นตั้งแต่แรก
**ไม่ใช่ผลของวันตัด** วันตัดแค่ทำให้เห็น

## 2. สิ่งที่ตกลงกันแล้ว

ถามผู้ใช้สามรอบ ทุกข้อมีคำตอบจากผู้ใช้ ไม่มีข้อไหนเดาเอง

| คำถาม | คำตอบ |
|---|---|
| ใบ `approved` ให้ HR เอาออกด้วยกลไกไหน | **ยกเลิกตรง ๆ พร้อมเหตุผล** ไม่ใช่สร้างคำขอถอนในนาม HR |
| HR ยกเลิกได้ถึงสถานะไหน | **ทุกสถานะที่ยังมีชีวิต** — `pending_mgr` · `pending_hr` · `approved` |
| ปุ่มอยู่จอไหน | **ตรวจสอบประจำเดือน** และ **ในกล่องฟอร์มแก้ไขใบ** |
| เหตุผลบังคับไหม | **บังคับ** |
| คำบนปุ่ม | **`ยกเลิก`** ไม่ใช่ `ยกเลิกใบ` หรือ `ยกเลิกใบนี้` |
| ปุ่มปิดฟอร์มเดิม (`ยกเลิก`) | เปลี่ยนเป็น **`ย้อนกลับ`** — **ทุกจอที่ใช้ฟอร์มนี้** ไม่ใช่เฉพาะจอ HR |
| ลำดับปุ่มในฟอร์ม | **`ยกเลิก` · `ย้อนกลับ` · `บันทึกการแก้ไข`** ชิดขวาทั้งหมด |
| `void` | **ถอนถาวร** — ฟีเจอร์ตายไปแล้ว |
| `ขอถอนใบ` ให้ HR ด้วยไหม | **ไม่** HR ไม่ต้องขอใคร จึงไม่มีปุ่มขอ |

### ทำไมยกเลิกตรง ๆ ไม่ใช่คำขอถอนในนาม HR

เสียสองข้อ และข้อที่สองเป็นกฎที่มีอยู่จริง

1. **สร้างบันทึกที่ไม่จริง** — ใบจะมี `withdrawal.requestedBy = HR` ทั้งที่พนักงาน
   ไม่ได้ขอ · ประวัติที่อ่านแล้วเข้าใจผิดว่าพนักงานเป็นคนเริ่ม
2. **ชนกฎเดิม** `withdrawDecisionPermission` ปฏิเสธไว้ว่า
   `ผู้ขอถอนไม่สามารถอนุมัติคำขอของตนเองได้` — HR ยื่นแล้วตัดสินเองจะติดกฎนี้
   ต้องไปเจาะข้อยกเว้นเพิ่ม ซึ่งคือการทำให้กฎอ่อนลงเพื่อรองรับเรื่องที่ไม่ควรเกิด

**HR เป็นลายเซ็นสุดท้ายอยู่แล้ว จึงไม่มีใครให้ "ขอ"** การขออนุญาตตัวเองไม่ใช่
ขั้นตอน มันคือพิธีกรรม

## 3. `void` — ถอนถาวร

`void` คือทางออกของ **`สร้างใบวันเกิดของเดือนนี้`** ซึ่งเป็นฟีเจอร์ที่ HR กดปุ่มเดียว
แล้วระบบเขียนใบ OT สวัสดิการวันเกิดให้ทุกคนที่เกิดเดือนนั้น **โดยไม่มีใครกรอกฟอร์ม**
ชั่วโมงมาจากปฏิทิน ไม่ได้มาจากคำบอกเล่าของใคร — และนั่นคือเหตุผลที่ `void`
ไม่บังคับเหตุผล: เหตุผลติดค้างเมื่อไปแก้ของที่*คนอื่นให้การไว้* แต่แถวที่ไม่เคยมีใคร
อ้างสิทธิ์ ไม่มีคำให้การอะไรให้ลบ

**ตัวสร้างถูกถอนไปแล้ว** `lib/birthdayEntries.js` ไม่มีในทรี · ของที่มาแทนคือ
`submit_hr_verified` — HR เปิด `วันเกิดที่ยังไม่มีใบ` อ่านเวลาจากเครื่องสแกนนิ้วมือ
พิมพ์เอง แล้วอนุมัติในทีเดียว · ผู้ใช้ยืนยัน 2026-09-15 ว่า **OT วันเกิดคีย์ตามปกติ
เหมือน OT วันอื่น ต่างแค่มีป้ายระบุ**

**บนฐานจริง: 0 ใบจาก 431 มี `submit_birthday` และ 0 ใบเคยถูก `void`** —
ปุ่ม `ถอนใบวันเกิด` ไม่เคยขึ้นบนจอเครื่องนี้เลย

### ลบอะไร เก็บอะไร

| ลบ | เก็บ |
|---|---|
| `UNTOUCHED_ACTIONS` · `isUntouchedSystemFiling` (lib/entries.js) | `SYSTEM_FILED_ACTIONS` · `isSystemFiled` — เป็น**ป้าย**สำหรับอ่านแถวเก่า ไม่ใช่ฟีเจอร์ |
| สาขา `void` ใน `cancelPermission` | `'void'` · `'submit_birthday'` ใน enum ของ `historySchema` |
| ปุ่ม `ถอนใบวันเกิด` + `voidEntry` ใน `HrEntries.jsx` และ `ApprovalQueue.jsx` | ป้ายไทยของสอง action นั้นใน `common.jsx` |
| สาขา `canVoid` ใน `ownFilingNote` — ยุบเหลือสตริงเดียว | |

**ทำไมยังไม่ล้าง enum** — *ผู้ใช้อยากล้างทั้งหมด และคำสั่งค้างอยู่ที่การนับบนกล่อง
Docker ก่อน* (คำสั่งที่ให้ไปคือ `docker compose exec app node --input-type=module
-e '…countDocuments({"history.action":"submit_birthday"})…'` ยิงจากในคอนเทนเนอร์
เพราะมันอ่าน `MONGODB_URI` ของเครื่องนั้นเอง) · ⚠ **และการนับฐานสองเครื่องยังไม่
ครอบชุดสำรอง** — `npm run restore` ที่เอา dump เก่ากว่าวันนี้กลับมา พาแถวแบบนั้น
กลับมาด้วยได้

เหตุผลเดิมของการเก็บไว้: ฐานเครื่องนี้มี 0 แถวก็จริง แต่**กล่อง Docker บน Linux
มี `mongod` ของตัวเอง** ([docker.md](docker.md)) ซึ่งยังไม่ได้นับ · ถ้าที่นั่นมีใบ
วันเกิดเก่าค้าง การตัดค่าออกจาก enum จะทำให้แถวนั้น validation ไม่ผ่านทันทีที่มี
อะไรไปแตะ — เป็นสิ่งที่คอมเมนต์ในสคีมาเตือนไว้เองอยู่แล้ว · สองคำนี้คือ**คำศัพท์
สำหรับอ่านของเก่า ไม่ใช่ฟีเจอร์** ฟีเจอร์คือปุ่มกับกฎ ซึ่งไปหมด

## 4. กฎ

`cancelPermission` ได้สาขาของ HR เหนือกฎเจ้าของใบ และได้พารามิเตอร์ `note`

```
cancelPermission(user, entry, note = '', { policy, on } = {})
```

**รูปเดียวกับ `editPermission` เป๊ะ** ไม่ใช่ความบังเอิญ — สองฟังก์ชันนี้วาดเส้นเดียวกัน
ที่ลายเซ็นแรก และอ่านคู่กันมาตลอด · ลำดับอาร์กิวเมนต์ที่ต่างกันคือที่มาของการเรียกผิด

| ลำดับ | เงื่อนไข | ผล |
|---|---|---|
| 1 | `mayCorrectEntries` + `rejected`/`cancelled` | 409 `รายการที่ไม่อนุมัติหรือยกเลิกแล้ว ยกเลิกซ้ำไม่ได้` |
| 2 | `mayCorrectEntries` + ไม่มีเหตุผล | 400 `กรุณาระบุเหตุผลการยกเลิก` |
| 3 | `mayCorrectEntries` | ✅ `action: 'hr_cancel'` |
| 4 | ไม่ใช่เจ้าของใบ | 403 เดิม |
| 5 | พ้นวันตัด | เดิม |
| 6 | มีลายเซ็นแล้ว | เดิม — ชี้ไปที่ `ขอถอนใบ` |
| 7 | | ✅ `action: 'cancel'` |

**HR ไม่ติดวันตัด** เพราะ `mayCorrectEntries` อยู่เหนือมัน เหมือน `แก้ไข` ทุกประการ —
นั่นคือความต่างทั้งหมดระหว่างวันตัดกับ `ปิดงวด` ที่ถูกถอนเมื่อ 2026-08-31

### `hr_cancel` ไม่ใช่ `cancel`

action คนละตัว ด้วยเหตุผลเดียวกับที่ `void` เคยเป็นคนละตัว และคอมเมนต์ในเราต์เขียนไว้
อยู่แล้ว: **`cancel` แปลว่าพนักงานถอนใบของตัวเอง** คนละเหตุการณ์ คนละผู้กระทำ
ประวัติที่พูดว่า *พนักงานยกเลิก* เกี่ยวกับสิ่งที่คนในฝ่ายบุคคลทำ คือประวัติที่โกหก

ป้ายไทยใน `common.jsx`: **`ฝ่ายบุคคลยกเลิกใบ`** · tone `off` เท่ากับ `cancel`

### คำขอถอนที่ค้างอยู่

ใบที่มี `withdrawal.state === 'requested'` ตอน HR กดยกเลิก — **ปิดคำขอนั้นเป็น
`granted` ไปพร้อมกัน ด้วยเหตุผลเดียวกัน** ปล่อยค้างไว้จะนับใน `withdrawalOpen`
ตลอดไปทั้งที่ใบตายแล้ว และ `periodItems` จะนับเป็นรายการค้างของงวดนั้นไม่มีวันหมด

## 5. จอ

### 5.1 ตรวจสอบประจำเดือน (`HrEntries.jsx`)

ปุ่ม **`ยกเลิก`** `btn ghost danger sm` พร้อมไอคอน `trash` วางถัดจาก `แก้ไข`
แสดงเมื่อ `mayEdit && !closed` — แถวที่ปิดแล้วมี `แก้ไขไม่ได้` พูดแทนอยู่แล้ว

กดแล้วเปิดกล่อง **`Modal` + footer ของตัวเอง ไม่ใช่ `ConfirmDialog`** เพราะ
`ConfirmDialog` ไม่มี `confirmDisabled` และปุ่มยืนยันต้องเทาจนกว่าจะพิมพ์เหตุผล ·
รูปนี้คือรูปเดียวกับกล่อง `ไม่อนุมัติคำขอถอนใบ` ใน `WithdrawalRequests.jsx`
(`dirty` · `<input maxLength={200}>` ใน `.field` · `.field-note` ใต้ช่อง) —
**สืบมา ไม่ได้ออกแบบใหม่**

- หัวกล่อง `ยกเลิกใบนี้` · subtitle = ชื่อ · วันที่ · ชั่วโมง
- `Alert kind="warn"` บอกว่าชั่วโมงจะถูกตัดออกจากเพดานแผนกและรายงานส่งบัญชี
  และ**แก้กลับไม่ได้**
- ช่องเหตุผลบังคับ · `.field-note` ว่า `จำเป็นต้องกรอก — พนักงานจะเห็นข้อความนี้บนรายการ`
- ปุ่ม `ไม่ยกเลิกแล้ว` / `ยืนยันการยกเลิก` (แดง) — คู่คำถาม-คำตอบแบบเดียวกับ
  `EmployeeView` ไม่ใช่ `ตกลง` / `ยกเลิก` ซึ่งเป็นคำถามกับการยักไหล่

**กล่องถูกวาดในทั้งสองสาขาของ `HrEntries`** — ทั้งสาขาตาราง และสาขา
`if (editing) return <OtForm/>` · `ConfirmDialog`/`Modal` พอร์ทัลออกไป จึงซ้อนบน
ฟอร์มได้ และ**นิยามอยู่ที่เดียว** ไม่ต้องมีไฟล์คอมโพเนนต์ใหม่ ไม่ต้องคัดลอกโค้ด

### 5.2 กล่องฟอร์มแก้ไขใบ (`OtForm.jsx`)

แถวปุ่มชิดขวาทั้งหมด: **`ยกเลิก`** (แดงจาง) · **`ย้อนกลับ`** · **`บันทึกการแก้ไข`**

- `ยกเลิก` วาดเมื่อได้รับ `onCancelEntry` เท่านั้น — ซึ่งมีแต่ `HrEntries` ที่ส่งมา
  ฟอร์มยื่นใบใหม่และฟอร์มบันทึกแทนไม่มีใบให้ยกเลิก
- **ปุ่มแดงไม่ติดปุ่มบันทึก** `ย้อนกลับ` คั่นกลาง — กดพลาดแล้วเสียหนักที่สุด
  ไม่ควรอยู่ไกลกันแค่ระยะนิ้วเดียวจากปุ่มที่กดบ่อยที่สุด

**`ยกเลิก` เดิมที่แปลว่าปิดฟอร์ม เปลี่ยนเป็น `ย้อนกลับ` ทุกจอ** — จอยื่นใบใหม่
จอบันทึกแทน และจอแก้ไขของ HR · ปล่อยให้คำเดียวแปลสองอย่างบนสองจอ คือความผิด
ชนิด *"กฎสองข้อที่ไม่ตรงกัน"* ที่ไฟล์ AGENTS.md ทั้งไฟล์เขียนขึ้นมาเพื่อกัน

⚠ **คอมเมนต์ที่ต้องเขียนใหม่ในคอมมิตเดียวกัน** `ConfirmDialog` ของฟอร์ม
(`แก้ใบของงวดที่ปิดแล้ว`) ใช้ `cancelLabel="ย้อนกลับ"` พร้อมเหตุผลว่า *"ในแอปนี้
ยกเลิก แปลว่ายกเลิกใบ OT และฟอร์มที่ยืนอยู่ข้างหลังกล่องนี้มีปุ่มที่ใช้คำนั้นอยู่"* —
ประโยคนั้นกลับด้านแล้ว: ตอนนี้ฟอร์มมีปุ่ม `ย้อนกลับ` **และ** ปุ่ม `ยกเลิก` ที่แปลว่า
ยกเลิกใบจริง ๆ · คำที่กล่องเลือกยังถูก เหตุผลไม่ใช่

### 5.3 คิวรออนุมัติ (`ApprovalQueue.jsx`)

ไม่เพิ่มอะไร **ลบอย่างเดียว** — ปุ่ม `ถอนใบวันเกิด` · `voidEntry` · สาขา `canVoid`
ใน `ownFilingNote` ซึ่งยุบเหลือสตริงเดียวและกลายเป็นค่าคงที่ · แถวที่ติด
`barredAsOwnFiling` เหลือ `WatchActions` อย่างเดียวเหมือนแถวอื่น

### 5.4 วัดจริงแล้ว — เจ็ดความกว้าง สองธีม

เรนเดอร์บน CSS ที่ build แล้ว (`.next-verify-hrcancel`) ใน Edge headless ·
ความกว้างต่ำกว่า 496 วัดผ่าน iframe เพราะหน้าต่าง headless ลงไม่ต่ำกว่านั้น

**ปุ่มแดงไม่เคยติดปุ่มบันทึก** — เหนือ 861 มี `ย้อนกลับ` คั่น ต่ำกว่านั้นอยู่คนละ

และ `rgb(255,169,142)` บน `rgb(31,39,35)` (ธีมมืด) — เป็นกฎที่มีอยู่แล้วในสไตล์ชีต
ไม่ได้เขียนสีใหม่

⚠ **ที่วัดคือการ์ดที่ประกอบขึ้นจาก CSS ที่ build แล้ว ไม่ใช่จอจริงหลังล็อกอิน** —
ตารางจริงบน ตรวจสอบประจำเดือน มีคอลัมน์มากกว่าในฮาร์เนส และตัวที่ยังพิสูจน์ไม่ได้
ด้วยวิธีนี้คือการกดจริง: กล่องเปิด/ปิด · เหตุผลที่พิมพ์เดินไปถึงเซิร์ฟเวอร์ ·
คำขอถอนที่ค้างถูกปิดจริง
