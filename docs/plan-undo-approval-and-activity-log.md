# แผน — ถอนการอนุมัติ และ ประวัติการทำรายการ

**สถานะ: ออกแบบเสร็จ ยังไม่เขียนโค้ด** · ตัดสินร่วมกับผู้ใช้ 2026-09-11

คำถามตั้งต้นคือ *"ควรเพิ่มหน้าประวัติการทำรายการทั้งหมดแบบรายทรานแซกชัน หรือให้ย้อน
สถานะได้ในหน้า รออนุมัติ และหน้าตรวจสอบ"* คำตอบที่ตกลงกันคือ **ทั้งสองอย่าง** เพราะ
มันแก้คนละครึ่งของปัญหาเดียวกัน — หน้าประวัติตอบว่า *เกิดอะไรขึ้น* ส่วนการถอยสถานะ

## 1. ปัญหาจริงสามเคสที่แผนนี้ต้องแก้

ผู้ใช้ระบุไว้ 2026-09-11 ว่าเจอมาแล้วทั้งสาม:

1. **กดอนุมัติผิด เพิ่งกด** — หัวหน้าหรือ HR กดผิดใบ/ผิดคน รู้ตัวทันที วันนี้ไม่มี
   ทางออกเลย ต้องไปขอให้พนักงานกด *ขอถอนใบ* ซึ่งผิดเรื่อง — กลไกนั้นมีไว้ให้
   **พนักงาน** ขอคืนใบของตัวเอง ไม่ใช่ให้ผู้เซ็นแก้ความผิดพลาดของตัวเอง
2. **เจอทีหลังว่าใบผิด** — ใบถูกเซ็นไปแล้วหลายวัน เพิ่งรู้ว่าเวลาผิด
3. **บัญชีทักว่าตัวเลขไม่ตรง** — ตัวเลขออกไปแล้ว ต้องย้อนกลับมาแก้

เคส 1 ไม่มีทางออกในระบบ · เคส 2 มีทางอ้อม (ให้พนักงานขอถอนใบ แล้วยื่นใหม่) ·
เคส 3 เริ่มจากหน้า **ตรวจสอบประจำเดือน** เสมอ และวันนี้พอ HR เจอใบที่ผิดตรงนั้น
ก็ไม่มีอะไรให้กดต่อ

## 3. ส่วนที่หนึ่ง — ถอนการอนุมัติ

### 3.1 สิ่งที่ **ไม่** ทำ และเหตุผล

ข้อเสนอตั้งต้นคือ *"ให้ย้อนสถานะได้"* แบบเลือกสถานะใหม่อิสระ **ตกไป** ผู้ใช้เลือก
เองว่าต้องเป็น **ถอยตามลำดับขั้น** และนั่นถูกกว่าด้วยเหตุผลเชิงโครงสร้าง:

- เลือกสถานะอิสระแปลว่าต้องตอบว่า *อนุมัติแล้ว → ปฏิเสธ* หมายความว่าอะไร ลายเซ็น
  หัวหน้าที่อยู่ข้างใต้ยังอยู่ไหม ใครเป็นคนปฏิเสธ — คำถามที่ไม่มีคำตอบที่ดี
- ถอยทีละขั้นลบลายเซ็นเดียวต่อครั้ง และ **มีที่ทางในระบบอยู่แล้ว**:
  `hrRejectReturnsTo: 'manager'` ใน `app/api/entries/[id]/reject/route.js` ส่ง
  `pending_hr` กลับไป `pending_mgr` มาตั้งแต่ต้น — ทิศทางถอยหลังไม่ใช่ของใหม่
  ในระบบนี้ เป็นเรื่องที่มีนโยบายกำกับอยู่แล้ว

### 3.2 เครื่องจักรสถานะ

```
approved  ──ถอนการอนุมัติ──▶  pending_hr  ──ถอนการอนุมัติ──▶  pending_mgr
          ลบ hrDecision                    ลบ managerDecision
          log: unapprove_hr                log: unapprove_mgr
```

- จาก `pending_mgr` — ไม่มีลายเซ็นให้ถอน → 409
- จาก `rejected` / `cancelled` — ใบตายแล้ว ให้ยื่นใหม่ → 409

**กดซ้ำได้ทันที** ใบที่ `approved` ถอยสองครั้งติดกันก็กลับถึง `pending_mgr` ได้
ไม่ต้องรอให้ใครเซ็นใหม่ก่อน — เคส "กดผิดทั้งสองขั้น" มีจริงและการบังคับให้เซ็นใหม่
เพื่อจะถอนอีกทีคือการขอให้คนเซ็นสิ่งที่เขารู้อยู่แล้วว่าผิด

### 3.3 ใครกดได้ — ตัดสิน 2026-09-11: **เจ้าของลายเซ็น + HR/admin เสมอ**

| ถอนลายเซ็นของ | ใครกดได้ |
|---|---|
| ฝ่ายบุคคล (`hrDecision`) | คนที่เซ็น (`hrDecision.by`) · role `hr` · role `admin` |
| หัวหน้า (`managerDecision`) | คนที่เซ็น (`managerDecision.by`) · หัวหน้าแผนกปัจจุบันหรือผู้รับช่วงที่ถือคิวนั้น · role `hr` · role `admin` |

ให้ HR/admin ถอยได้ทุกขั้นเพราะ **เคส "บัญชีทัก" มาถึง HR ไม่ใช่หัวหน้า** และ
หัวหน้าที่เซ็นอาจลาออกหรือย้ายแผนกไปแล้ว การผูกไว้กับเจ้าของลายเซ็นอย่างเดียว
จะทำให้มีใบที่ถอนไม่ได้เลย

ฝั่งหัวหน้าให้ตัดสินผ่าน `departmentClaim` ใน `lib/delegation.js` — ตัวเดียวกับที่
คิวอนุมัติและ `withdrawDecisionPermission` ใช้ ผู้รับช่วงจึงเอื้อมถึงทีมที่ตัวเองคุม
พอดี และประวัติบันทึกว่าทำแทนใคร

**พนักงานเจ้าของใบกดไม่ได้** — ของเขาคือ *ขอถอนใบ* ที่มีอยู่แล้ว

### 3.4 เหตุผล — บังคับ

บังคับเสมอ ไม่มีข้อยกเว้น เหมือน *ไม่อนุมัติ* และ *ฝ่ายบุคคลแก้ไข* · เพดาน
200 ตัวอักษร เท่ากับ `rejectionReason` และ `withdrawal.reason`

### 3.5 สิ่งที่เขียนลงฐานข้อมูล

1. `entry.status` ถอยหนึ่งขั้น
2. ลบ `entry.hrDecision` หรือ `entry.managerDecision` (`undefined`)
3. `entry.log(user, 'unapprove_hr' | 'unapprove_mgr', reason, from, null, historyExtra(may))`
4. `overCeilingReason` — คำนวณใหม่จากลายเซ็นที่ยังเหลือด้วย
   `needsOverCeilingReason` ถ้าไม่เหลือลายเซ็นแล้วก็ล้างทิ้ง มิฉะนั้นรายงานส่งบัญชี
   จะแสดงเหตุผลของลายเซ็นที่ถูกถอนไปแล้ว
5. **ไม่ลบแถวประวัติเดิมสักแถว** ลายเซ็นที่หายจากตัวเอกสารยังอยู่ในประวัติ —
   นี่คือสิ่งที่ทำให้ *ถอนการอนุมัติ* ไม่ใช่การลบหลักฐาน

เพิ่มสองค่าเข้า enum ของ `historySchema`: `unapprove_mgr` `unapprove_hr`
และเพิ่มสองแถวใน `ACTION_META`

### 3.6 สิ่งที่ต้องปฏิเสธ

| กรณี | รหัส | ข้อความ |
|---|---|---|
| `pending_mgr` | 409 | ใบนี้ยังไม่มีใครเซ็น ไม่มีการอนุมัติให้ถอน |
| `rejected` / `cancelled` | 409 | ใบนี้ปิดแล้ว ถอนการอนุมัติไม่ได้ ให้พนักงานยื่นใหม่ |
| มีคำขอถอนใบค้างอยู่ (`hasOpenWithdrawal`) | 409 | ใบนี้มีคำขอถอนรออยู่ ให้ตอบคำขอนั้นก่อน |
| ไม่มีสิทธิ์ | 403 | ถอนการอนุมัติได้เฉพาะผู้ที่เซ็น หัวหน้าของแผนกนั้น หรือฝ่ายบุคคล |
| ไม่มีเหตุผล | 400 | กรุณาระบุเหตุผลที่ถอนการอนุมัติ |

แถวที่สามสำคัญ: ถ้าปล่อยให้ทั้งสองกลไกทำงานพร้อมกันบนใบเดียว จะมีสองทางที่ทำให้ใบ
ออกจาก `approved` และไม่มีทางบอกว่าอันไหนชนะ

## 4. ส่วนที่สอง — แท็บ ประวัติการทำรายการ

### 4.1 สิทธิ์ — ตัดสิน 2026-09-11: **ฝ่ายบุคคล + ผู้ดูแลระบบ**

ต่างจาก `บันทึกประวัติระบบ` ที่เป็น admin เท่านั้น เพราะหน้านี้พูดเรื่อง **ใบ OT**
ไม่ใช่เรื่องพฤติกรรมคน — เหตุผลที่ `app/api/logs/route.js` กันฝ่ายบุคคลออกจาก
บันทึกระบบไม่ใช้กับหน้านี้ · หัวหน้างานยังไม่ให้ (ต้องเขียน scope เพิ่ม และคิวของ
เขาเล็กพอที่จะไม่ต้องใช้)

### 4.2 หน้าตา — ตัดสิน 2026-09-11: **สมุดรายวัน เรียงตามเวลา**

แถวละเหตุการณ์ ใหม่สุดอยู่บน ตอบคำถาม *"เมื่อวานมีใครทำอะไรบ้าง"* ได้ทันที
(แบบจัดกลุ่มตามใบ และแบบจัดกลุ่มตามคน ถูกเสนอและตกไป — สองแบบนั้นตอบคำถามนี้ไม่ได้
โดยไม่กวาดทั้งหน้า)

ตาราง `stack-table` ห้าคอลัมน์ ตามแบบ `components/HrEdits.jsx`:

| คอลัมน์ | เนื้อหา | กฎ |
|---|---|---|
| เมื่อไหร่ | `thaiStamp(h.at)` | `nowrap` — วันที่ไม่ตัดบรรทัด |
| ผู้ทำ | `byName` · บรรทัดรอง `ทำแทน {ชื่อ}` หรือ `ผู้ดูแลระบบเซ็นแทน` | ชื่อคนตัดบรรทัดได้ ตัดที่ช่องว่าง ไม่ตัดกลางคำไทย |
| การกระทำ | `ACTION_META[h.action].label` + ชิป `{จาก} → {ถึง}` เมื่อสถานะขยับ + เหตุผลใต้ | |
| ใบ / พนักงาน | ชื่อ + รหัส + วันที่ OT + ชั่วโมง + `StatusChip` สถานะ**ปัจจุบัน** · กดแล้วเปิดป๊อปอัปใบ | `min-width: 0` |
| สิ่งที่เปลี่ยน | `<Changes before after />` เฉพาะแถวที่มี `before` | เต็มความกว้าง ไม่มีป้ายเบียด |

ใต้ตาราง: pager แบบเดียวกับตารางอื่นทั้งแอป (`PAGE_SIZES` สี่ค่า — ดู
`test/tablePager.test.js` และ `components/HrView.jsx` เป็นต้นแบบ)

### 4.3 มือถือ (ต่ำกว่า 860px)

`stack-table` + `data-label` ชุดเดิมที่ทุกตารางรายการในแอปใช้ — การ์ดละเหตุการณ์
หัวการ์ดคือ **เวลา + การกระทำ** (คือสองอย่างที่คนกวาดตาหา) ที่เหลือเป็นแถวมีป้าย
· `min-width: 0` บนช่องชื่อ · ไม่มีแถบเลื่อนแนวนอนบนตัวหน้า · เป้ากด 44px

### 4.4 ตัวกรอง

แถวเดียวเหนือตาราง ใช้ `PickerBox` / `usePicker` — ห้าม `<select>` ของเบราว์เซอร์

- **เดือน** — ตั้งต้นคือ **เดือนปัจจุบัน** ตัดสิน 2026-09-11
- **ประเภทเหตุการณ์** — จัดกลุ่ม 18+2 action ให้เหลือชื่อที่คนรู้จัก: ทั้งหมด ·
  ยื่นคำขอ · อนุมัติ · ไม่อนุมัติ · **ถอนการอนุมัติ** · แก้ไข · ขอถอนใบ · ยกเลิก ·
  คำนวณใหม่ตามนโยบาย
- **แผนก**
- **ค้นหา** — ชื่อ/รหัสพนักงาน/เหตุผล

**ตั้งต้นคือ เดือนนี้ ทุกเหตุการณ์** ไม่กรองอะไรออก ตัดสิน 2026-09-11 — ตรงกับ
ทุกหน้าในแอปที่เปิดมาที่เดือนปัจจุบัน และเปลี่ยนเดือนได้ด้วยตัวเลือกอันเดียวกัน

### 4.5 ข้อมูลมาจากไหน — **ไม่มี endpoint ใหม่**

ใช้ `GET /api/entries?period=…&scope=report` ที่มีอยู่แล้ว (ละ `employee` ได้ คืน
ทั้งเดือนของทุกคนในขอบเขต) แล้วให้หน้าจอแผ่ `entry.history` เป็นแถว ด้วย `editsOf()`
ตัวเดิม — **ตรงกับที่ `components/HrEdits.jsx` ทำอยู่แล้ว**

ทำแบบนี้เพราะการจับคู่ `before` กับ `after` ต้องเดินประวัติถอยหลังทั้งใบ
(`editsOf` ทำอยู่) ถ้าเขียน aggregation `$unwind` ฝั่งเซิร์ฟเวอร์จะได้ code path
ที่สองสำหรับเรื่องเดียวกัน และมีแค่อันเดียวที่จะถูกแก้ตอนมีบั๊ก

**ถ้าช้าค่อยว่ากัน** หนึ่งเดือนของพนักงานห้าสิบคนบน LAN — วัดก่อน แล้วค่อยตัดสิน
ว่าจะเพิ่ม `GET /api/entries/activity` ไหม ไม่ใช่เดาตอนนี้

### 4.6 ที่อยู่ในเมนู

แท็บใหม่ `key: 'activity'` · `label: 'ประวัติการทำรายการ'` · `group: 'work'` ·

เรื่องยังอยู่ในประวัติรายการ

## 8. สิ่งที่จงใจไม่อยู่ในแผนนี้

- **เลือกสถานะใหม่อิสระ** — เหตุผลใน §3.1
- **ถอนย้อนจาก `rejected` / `cancelled`** — ใบตายแล้ว ให้ยื่นใหม่ กลไก
  `refiledFrom` ผูกใบใหม่กับใบเก่าให้อยู่แล้ว
- **แจ้งเตือนพนักงาน** — ระบบไม่มีช่องทางแจ้งเตือนเลย ป้ายบนแถวใบ (§5) คือสิ่งที่
  ทำได้จริงวันนี้
- **ตรวจว่าเดือนถูกพิมพ์/ส่งบัญชีไปแล้วหรือยัง** — ไม่มีข้อมูลในระบบ (§2) ·
  `otAccessLogs` บันทึกทุก request รวมทั้ง `GET /api/exports/accounting.csv`
  จึง**พอจะ**ตอบได้ว่าใครดึงรายงานเดือนไหนไปเมื่อไหร่ — แต่นั่นคือการเดาเจตนาจาก
  ล็อกจราจร และผิดวัตถุประสงค์ของคอลเลกชันนั้น ถ้าจะทำจริงควรเป็นฟิลด์ที่บันทึก
  โดยตรง ซึ่งเป็นงานคนละชิ้น
- **`GET /api/entries/activity` แยกต่างหาก** — ทำเมื่อวัดแล้วว่าช้าจริง (§4.5)
- **เส้นตัดเวลาว่าถอนได้ภายในกี่นาที/กี่วัน** — เคยเสนอ ตกไป เพราะเคส "บัญชีทัก"
  มาถึงหลังสิ้นเดือน เส้นตัดใด ๆ จะตัดเคสนั้นออกพอดี
