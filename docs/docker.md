## เรื่องพอร์ต — คำตอบสั้น ๆ คือไม่ต้องแก้อะไร

**ไม่ต้องเปลี่ยนพอร์ตของแอปเพื่อลง Docker** และที่จริง**เปลี่ยนจาก environment
ไม่ได้ด้วย**: `start` ใน package.json คือ `next start -p 3000` และ `-p` ชนะ
`$PORT` เสมอ — บรรทัด `PORT=3000` ใน `.env` กับ `.env.example` จึงเป็นบรรทัดตาย
มาตั้งแต่ต้น ทั้งในคอนเทนเนอร์และนอกคอนเทนเนอร์ ถ้าจะย้ายพอร์ตจริงต้องแก้ flag
ในสคริปต์ ไม่ใช่ตั้งตัวแปรสภาพแวดล้อม

และเพราะคอนเทนเนอร์ใช้ network stack ของเครื่องโดยตรง `ports:` ใน compose ก็ไม่มี
ผลเช่นกัน — แอปเปิด `:3000` ของเครื่องตรง ๆ ไม่มีการ map

## ทำไมต้อง `network_mode: host`

`mongod` ตัวนี้ฟังแค่ loopback และ URI ไม่มี username/password — **การที่มันฟังแค่
loopback คือสิ่งที่ทำหน้าที่แทนรหัสผ่านอยู่** ถ้าเอาแอปไปไว้ใน bridge network
`127.0.0.1` ในคอนเทนเนอร์จะหมายถึงตัวคอนเทนเนอร์เอง ทางออกจะเหลือสองทางและทั้งคู่
แย่กว่า:

- แก้ `bindIp` ของ mongod ให้รับ `172.17.0.1` ด้วย = เปิดฐานข้อมูลที่ไม่มีรหัสผ่าน
  ให้คอนเทนเนอร์ **ทุกตัวบนเครื่อง** ซึ่งเครื่องนี้มีอยู่หลายสิบตัว
- ย้าย MongoDB เข้ามาเป็น service ใน compose = ต้องย้ายข้อมูลจริงและมีฐานข้อมูล
  สองที่ระหว่างทาง

`network_mode: host` ไม่ต้องทำทั้งสองอย่าง `MONGODB_URI` ใน `.env` ใช้ได้ตามที่
เขียนอยู่แล้ว **ไม่มีบรรทัดไหนใน `.env` ต้องแก้เลย** ยกเว้น `NODE_ENV` ซึ่ง
compose ทับให้เป็น `production` ให้เอง (ค่าใน `environment:` ชนะ `env_file:`)

ราคาที่จ่ายคือมันผูกกับ Linux วันที่ย้ายไป Windows Server ไฟล์นี้ใช้ไม่ได้ตามที่
เขียน ต้องกลับไปเป็น bridge + `ports:` + แก้ bindIp และนั่นคือคนละการติดตั้ง

## ก่อน up ครั้งแรก: ต้องไม่มีอะไรถือ :3000

ภายใต้ host networking คอนเทนเนอร์แย่งพอร์ตกับโปรเซสบนเครื่องตรง ๆ ถ้ามี
`next start` หรือ `next dev` ค้างอยู่ คอนเทนเนอร์จะ `listen EADDRINUSE` แล้ว
**วนรีสตาร์ทเงียบ ๆ** ตาม `restart: unless-stopped`

> 🔴 **และมันหลอกคนได้ ซึ่งเกิดขึ้นจริงแล้วตอนเขียนไฟล์นี้ 2026-09-09**
> คอนเทนเนอร์ตัวแรกวนรีสตาร์ทด้วย EADDRINUSE ตั้งแต่ครั้งแรกที่บูต — ไม่เคยรับงาน
> เลยสักครั้ง — แต่ `curl http://127.0.0.1:3000/api/health` ตอบ **200 พร้อม
> `database.ok: true`** ทำให้ดูเหมือน deploy สำเร็จ
>
> ตัวที่ตอบ 200 คือ `next-server` ที่มีคนสั่งรันบนเครื่องจากเซสชัน ssh เมื่อ
> 01:13 น. ของวันนั้น มันถือพอร์ตอยู่ก่อน คอนเทนเนอร์จึงไม่เคยได้พอร์ต
>
> **health check ตอบ 200 ไม่ได้แปลว่าคอนเทนเนอร์ของคุณคือตัวที่ตอบ** เป็นความ
> ผิดพลาดตระกูลเดียวกับที่ `scripts/deploy.ps1` ขั้นที่ 5 มีไว้ดัก — BUILD_ID
> ใหม่บนดิสก์ไม่ได้แปลว่าเซิร์ฟเวอร์ที่รันอยู่กำลังเสิร์ฟมัน

### วิธีดูว่าใครถือพอร์ตอยู่จริง

```bash
pid=$(ss -ltnpH 'sport = :3000' | grep -oP 'pid=\K[0-9]+' | head -1)
cat /proc/$pid/cgroup
```

- ขึ้นว่า `/system.slice/docker-<id>.scope` → **คอนเทนเนอร์เป็นคนตอบ** ถูกต้อง
- ขึ้นว่า `/user.slice/.../session-N.scope` → เป็นโปรเซสที่คนรันไว้บนเครื่อง
  ไม่ใช่คอนเทนเนอร์ ต้องหยุดมันก่อน (`ls -l /proc/$pid/cwd` บอกว่ามันรันจาก
  โฟลเดอร์ไหน ก่อนตัดสินใจฆ่า)

ตรวจซ้ำอีกด้าน — สถานะคอนเทนเนอร์ต้องเป็น `Up` ไม่ใช่ `Restarting`:

```bash
docker compose ps
docker compose logs --tail=20 app
```

## เขตเวลา

อิมเมจฐานเป็น UTC จึงตั้งไว้ทั้งสองค่าใน `Dockerfile` และย้ำอีกครั้งใน compose:

- `TZ=Asia/Bangkok` — เขตเวลาของโปรเซส
- `OT_TIMEZONE=Asia/Bangkok` — เขตเวลาที่ระบบใช้**ตัดสินว่าเป็นของวันไหน**

ค่าหลังมี fallback เป็น `Asia/Bangkok` อยู่แล้วใน `lib/today.js` แต่ `.env.example`
เขียนไว้ตรง ๆ ว่าบนเซิร์ฟเวอร์ให้ตั้งให้เห็นด้วยตา เพราะมันคือบรรทัดเดียวที่กัน
กะที่เลิก 00:30 ไม่ให้ไปนับเป็นวันถัดไป ตรวจได้ด้วย:

```bash
docker compose exec app node -e "console.log(new Date().toString())"
# ต้องลงท้ายด้วย GMT+0700 (Indochina Time)
```

## ชุดสำรอง

compose ผูก `./backups` ของ repo เข้ากับ `/app/backups` ในคอนเทนเนอร์ และ**ไม่ได้
ตั้ง** `BACKUP_DIR` — ซึ่งให้พฤติกรรมเดียวกับที่เป็นอยู่ตอนนี้เป๊ะ คือแอปมองหา
ชุดสำรองที่ `./backups` ของตัวเอง รายงานสถานะ `sameDisk` และไม่ขึ้นแบนเนอร์

วันที่ย้ายชุดสำรองไปดิสก์นอกจริง ต้องแก้ **สองที่ให้ตรงกัน** และไม่มีอะไรบังคับ
ให้มันตรง: path ที่ `scripts/backup.sh` เขียนลงไป กับ `BACKUP_DIR` ที่แอปอ่าน
ถ้าไม่ตรง แอปจะรายงานโฟลเดอร์ว่างขณะที่ dump กองอยู่อีกที่ ตัวอย่างที่ถูกอยู่ใน
คอมเมนต์ของ `docker-compose.yml`

คำสั่งที่มีคนพิมพ์

URL แบบ `trycloudflare.com` เป็นของแจกฟรีแบบไม่ต้องมีบัญชี Cloudflare และ
**ไม่ผูกกับใครเลย** — คอนเทนเนอร์รีสตาร์ทเมื่อไหร่ (เครื่องรีบูต, `docker restart`,

นี่คือปัญหาเดียวกันกับที่ docs/network.md บันทึกไว้ว่าเคยเกิดจริง — `192.168.109.119`

**อย่าแจก URL นี้ให้พนักงานทั้งบริษัทจด** มันเหมาะกับการให้คนนอกเข้ามาดูชั่วคราว

### ทำให้ชื่ออยู่ถาวร — named tunnel

ฝั่งเซิร์ฟเวอร์พร้อมแล้วตั้งแต่ 2026-09-09: บริการ `tunnel-named` ใน
`docker-compose.yml` อยู่ใต้ profile `public-named` รออยู่ ที่เหลือคือของที่ทำได้
เฉพาะบนบัญชี Cloudflare เท่านั้น

**บน dashboard** (Zero Trust → Networks → Tunnels):

1. **Create a tunnel** → เลือก **Cloudflared** → ตั้งชื่อ เช่น `primus-ot` → Save
2. หน้าที่ขึ้นมาจะโชว์คำสั่งติดตั้งพร้อม**โทเคนยาว ๆ ที่ขึ้นต้นด้วย `eyJ`** —
   ก๊อปเฉพาะโทเคน ไม่ต้องเอาคำสั่ง เพราะคอนเทนเนอร์รันให้อยู่แล้ว
3. แท็บ **Public Hostname** → **Add a public hostname**
   - **Subdomain** — เช่น `ot`
   - **Domain** — โดเมนที่อยู่ในบัญชี
   - **Path** — เว้นว่าง
   - **Service** → **Type: HTTP** · **URL: `127.0.0.1:3000`**

   ที่ต้องเป็น `127.0.0.1` ไม่ใช่ชื่อ service ของ compose เพราะคอนเทนเนอร์อุโมงค์
   ใช้ network ของเครื่อง (`network_mode: host`) พอร์ต 3000 ของเครื่องคือแอปโดยตรง

**บนเซิร์ฟเวอร์** — เติมโทเคนลงท้าย `.env` (ไฟล์นี้ไม่เข้า git):

```bash
echo 'TUNNEL_TOKEN=eyJ...ที่ก๊อปมา...' >> .env
docker compose stop tunnel                       # ปิดอุโมงค์ชั่วคราวก่อน
docker compose --profile public-named up -d      # เปิดอุโมงค์ถาวร
docker compose logs --tail=20 tunnel-named       # ต้องเห็น Registered tunnel connection
```

TLS ของ hostname นั้น Cloudflare ออกให้เองเมื่อโดเมนอยู่ในบัญชี ไม่ต้องทำใบรับรอง

**เลิกใช้อุโมงค์ชั่วคราวเมื่อตัวถาวรเดินแล้ว** — `docker compose rm -sf tunnel`
ใช้พร้อมกันสองตัวได้ก็จริงแต่ไม่มีเหตุผล และทำให้ตอบไม่ได้ว่าคนเข้ามาทางไหน

**โทเคนคือสิทธิ์เปิดอุโมงค์เข้ามาในเครือข่ายนี้** ไม่ใช่แค่ชื่อโดเมน หลุดเมื่อไหร่
ให้ไป rotate ที่ dashboard ทันที มันอยู่ใน `.env` ที่เดียว และ cloudflared อ่านชื่อ
ตัวแปร `TUNNEL_TOKEN` เอง จึงไม่ต้องเขียนลง `command` ที่ `docker inspect` มองเห็น

### อะไรกันอยู่ อะไรไม่ได้กัน

**กันอยู่** — ทุก endpoint ที่ไม่ใช่ `/api/health` ตอบ 401 เมื่อไม่มี session
(เดินจริงผ่าน URL สาธารณะแล้ว) · ข้อความล็อกอินผิดเป็นข้อความเดียวกันไม่ว่ารหัส
พนักงานจะมีจริงหรือไม่ จึงไม่บอกใบ้ว่าบัญชีไหนมีอยู่ · `lib/loginThrottle.js` หน่วง
การเดารหัสผ่าน · คุกกี้ออกแบบ `Secure` เพราะ `isHttpsRequest` อ่าน
`x-forwarded-proto` ที่ Cloudflare ส่งมา

**ไม่ได้กัน** — ใครก็ตามที่มี URL เปิดหน้าล็อกอินได้ ไม่มีการจำกัด IP และไม่มี
Cloudflare Access คั่นหน้า · `--protocol http2` ทำให้อุโมงค์เดินได้บนเครือข่ายนี้
ที่บล็อก QUIC ขาออก แต่ไม่ได้เพิ่มความปลอดภัยอะไร · **ฐานข้อมูลไม่ได้ออกไปด้วย**
mongod ยังฟังแค่ `127.0.0.1` และอุโมงค์ชี้ไปที่พอร์ตของแอปเท่านั้น

## เรื่องที่ Docker แก้ให้ และเรื่องที่ยังไม่แก้

`restart: unless-stopped` คือคำตอบของปัญหาที่ README §Status บันทึกไว้ว่า **ไม่มี
อะไรปลุกแอปกลับมาเลย** — ทั้งกรณีแอปตายเองและกรณีเครื่องรีบูต โดยมีเงื่อนไขข้อเดียว
คือ docker daemon ต้องถูกตั้งให้ขึ้นตอนบูต (`systemctl enable docker`)

และ `docker compose up -d --build` **ไม่ทำให้แอปที่รันอยู่ล่ม** ซึ่งเป็นปัญหาที่
AGENTS.md เตือนเรื่อง `npm run build` ทับ `.next` ของ `next start` ที่รันอยู่ —
ที่นี่ build เกิดในอิมเมจ ตัวเก่ายังเสิร์ฟ `.next` ของตัวเองจนกว่าจะถูกสลับในก้าว
เดียว (วิธี VERIFY_DIST_DIR ยังเป็นวิธีของการ build บนแล็ปท็อป และ **ห้ามตั้ง**
`VERIFY_DIST_DIR` ในอิมเมจ เพราะ `next start` จะไปหา distDir ที่ไม่เคยถูก build)

**สิ่งที่ยังไม่ได้ทำ — รายการนี้คือสภาพจริง ให้รักษาให้ทันสมัย ไม่ใช่ทำให้ดูเรียบร้อย:**

- **อิมเมจ 955 MB** เพราะยกทั้ง `node_modules` ของ production เข้าไป ทางลดคือ
  `output: 'standalone'` ใน `next.config.js` ซึ่งเป็นการแก้พฤติกรรมของ build
  จึงยังไม่ได้ทำ
- **ไม่มี reverse proxy ของตัวเอง** — แอปเปิด `:3000` บนทุก interface ของเครื่อง
  ตรง ๆ ใน LAN ยังเป็น HTTP ล้วน · ทาง**อินเทอร์เน็ต**ได้ TLS จากขอบของ Cloudflare
  ตั้งแต่ 2026-09-09 (บรรทัดนี้เคยอ่านว่า "**ไม่มี reverse proxy และไม่มี TLS**")
  แต่ระหว่าง cloudflared กับแอปยังเป็น HTTP บน loopback ซึ่งไม่เป็นไร
  เรื่องชื่อโดเมนภายในและใบรับรองของ LAN ยังอยู่ใน docs/network.md
- **healthcheck ไม่ได้รีสตาร์ทอะไรเอง** Docker ไม่รีสตาร์ทคอนเทนเนอร์ที่เป็น
  `unhealthy` — มันรีสตาร์ทเฉพาะตอนโปรเซสตาย ค่า healthcheck ที่ใส่ไว้จึงมีไว้ให้
  `docker compose ps` กับคนที่มาดู ไม่ใช่ระบบกู้คืนอัตโนมัติ
- **ยังไม่เคยรันบน Windows / Docker Desktop** และตามที่เขียนไว้ข้างบน มันจะไม่ทำงาน
  ตามไฟล์นี้ที่นั่น

## ทดสอบอะไรไปแล้วบ้าง

แถวที่ทำเครื่องหมาย **(deploy จริง)** เดินบนคอนเทนเนอร์ที่เสิร์ฟอยู่ตอนนี้เมื่อ
2026-09-09 ส่วนแถวที่เหลือเดินก่อนหน้านั้นบนคอนเทนเนอร์ทดสอบที่พอร์ต 3010:

| ทดสอบ | ผล |
|---|---|
| `docker compose build` | ผ่าน · ไม่ต้องมี `.env` ตอน build |
| **(deploy จริง)** คอนเทนเนอร์เป็นตัวที่ถือ `:3000` | cgroup ของ pid ที่ฟังอยู่ = `docker-9af466b4e16a….scope` ตรงกับ container id |
| **(deploy จริง)** ต่อฐานข้อมูลจริงได้ | `/api/health` → 200, `database.ok: true`, latency 2 ms |
| **(deploy จริง)** healthcheck ของ Docker | `docker compose ps` → `Up (healthy)` |
| หน้าแรกเสิร์ฟได้ | HTTP 200 ทั้งใน LAN และผ่าน URL สาธารณะ |
| เขตเวลา | `GMT+0700 (Indochina Time)`, `NODE_ENV=production` |
| สคริปต์ดูแลระบบ | `npm run whatif -- --show` อ่านนโยบายจากฐานจริงได้ |
| ด่านค่าสภาพแวดล้อมที่ขาด | รันโดยไม่ส่ง env → exit **1** พร้อมข้อความบอกว่าขาดตัวไหน |
| **(deploy จริง)** API ที่ต้องล็อกอิน ผ่าน URL สาธารณะ | `/api/entries`, `/api/employees`, `/api/exports/logs.csv` → **401** ทุกตัว |
| **(deploy จริง)** ล็อกอินผิด ผ่าน URL สาธารณะ | **401** ข้อความเดียวกันไม่ว่ารหัสพนักงานจะมีจริงหรือไม่ · ยิงซ้ำแล้ว `loginThrottle` เริ่มหน่วง |

ที่**ยังไม่ได้**ทดสอบ และควรเป็นสิ่งแรกที่คนมีบัญชีลองทำ:

- **ล็อกอินสำเร็จจริงผ่าน URL สาธารณะ** — ไม่มีรหัสผ่านของใครจึงเดินไม่ได้ ที่ตรวจ
  ไปคือ*อ่านโค้ด*: `isHttpsRequest` อ่าน `x-forwarded-proto` เป็นอันดับแรก และ
  Cloudflare Tunnel ส่งหัวนั้นมาเป็น `https` คุกกี้จึงควรออกมาแบบ `Secure` ถูกต้อง
  — แต่ "ควร" กับ "เดินแล้ว" ไม่ใช่คำเดียวกัน และเรื่องคุกกี้นี้เคยพังมาแล้วครั้งหนึ่ง
  (ดูหัวไฟล์ `lib/httpsRequest.js`)
- ยื่นใบ / อนุมัติ / พิมพ์ ในคอนเทนเนอร์
- รีบูตเครื่องแล้วดูว่าแอปกลับมาเอง (`restart: unless-stopped` ควรทำให้กลับ แต่ยัง
  ไม่มีใครรีบูตเพื่อพิสูจน์)
- `npm run backup` เขียนลง volume จริง
